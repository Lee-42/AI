## 01 Grounded Prompt、欢迎语、记忆与安全降级

### 本节目标

这一节先实现四个 Provider 无关的策略组件，不急着接入 Mock、调试 API 或 RTC：

```text
固定欢迎语
   + 有界 Session 记忆
   + Grounded Prompt
   + 安全降级决策
   -> 下一节的 RAG Service
```

它们都可以离线测试，不会调用火山模型、Chroma Cloud 或 RTC，也不会产生云费用。

### 1. 组合两份策略，不复制规则

项目已经有两份版本化策略：

| 策略 | 负责什么 |
| --- | --- |
| [`customer-service-policy.v1.json`](../voice-customer-service-lab/config/customer-service-policy.v1.json) | AI 身份、欢迎语、隐私、表达风格和 Session 记忆预算 |
| [`rag-answer-policy.v1.json`](../voice-customer-service-lab/config/rag-answer-policy.v1.json) | 证据规则、Grounded 指令、生成参数和固定降级文案 |

如果再创建一份“实时 RAG 大 Prompt”，身份、隐私和拒答规则就会出现多个副本，修改时很容易
只更新其中一份。因此 [`RealtimeConversationPolicy`](../voice-customer-service-lab/apps/api/src/ai/realtime-conversation-policy.ts)
只组合两份策略，并生成稳定的组合版本：

```text
commerce-cs-zh-cn@... + commerce-rag-zh-cn@...
```

两份策略的 Locale 不一致时直接启动失败，避免把中文客服策略和其他语言的 RAG 策略误拼在
一起。

### 2. Grounded Prompt：History 不是 Evidence

[`GroundedPromptBuilder`](../voice-customer-service-lab/apps/api/src/ai/grounded-prompt-builder.ts)
把 System Instruction 固定为四个区段：

```text
[GROUNDED ANSWER POLICY]
[CONVERSATION HISTORY BOUNDARY]
[IDENTITY AND PRIVACY]
[VOICE RESPONSE]
```

最重要的边界是区分历史与本轮证据：

| 输入 | 用途 | 能否证明商城现行政策 |
| --- | --- | --- |
| `History` | 理解“它”“刚才那个”等指代 | 不能 |
| 当前问题 | 表达用户需求 | 不能 |
| 本轮 `EVIDENCE` | 支持金额、期限、条件和结论 | 可以，但仍需有效性与冲突门禁 |

例如上一轮 AI 曾说“退货期是七天”，这一轮也不能直接复用这句话作为证据；必须重新以本轮
检索到的有效来源为准。否则旧答案一旦错误或过期，就会在后续对话中自我强化。

Prompt 是模型行为约束，不是权限系统。Tenant 隔离、工具授权、证据 Allowlist 和引用校验仍
必须由服务端代码执行。

### 3. 欢迎语为什么固定生成？

欢迎语属于产品文案，不需要推理：

```text
创建会话 -> 读取版本化欢迎语 -> 播放/展示
```

它不会调用 Router、Retriever 或 LLM，因此具有四个好处：延迟稳定、零模型费用、不会幻觉、
容易做合规审核。欢迎语也不写入 Session 记忆，因为它不是一次用户问答，重复加入只会浪费
上下文预算。

后续可以按品牌或 Locale 选择不同版本，但仍应由受控配置决定，而不是让 LLM 临场发挥。

### 4. Session 记忆：有用，但必须有界

[`SessionConversationMemory`](../voice-customer-service-lab/apps/api/src/ai/conversation-memory.ts)
以服务端可信的 `tenantId + sessionId` 为作用域，只保存已经完整结束的用户/AI 问答对：

- 最多 6 个完整轮次、估算 512 Tokens，先淘汰最旧整轮；
- 单轮本身超预算时整轮拒绝，不截断其中一半；
- 用户或 AI 任一侧命中敏感类别时，整轮都不保存；
- 失败、取消、流式 Delta 和欢迎语不进入记忆；
- Session 关闭时调用 `clear(scope)`，不跨 Session 保存画像。

这里要区分两个容易混淆的配置：

| 配置 | 含义 |
| --- | --- |
| `generation.history_length` | 火山 Voice Agent 的 Provider 原生历史参数 |
| `conversation_memory` | 本应用可测试的隔离、敏感排除、Token 预算和清理边界 |

只配置 Provider 的 `HistoryLength`，不能证明敏感内容已排除，也不能证明 Session 结束后数据已
清理。

课程中的 [`BasicSensitiveConversationDetector`](../voice-customer-service-lab/apps/api/src/ai/sensitive-conversation-detector.ts)
只识别明确的密码、验证码、手机号、卡号和安全码格式，并且只返回类别，不返回命中原值。
它用于讲清 Port 与生命周期，不等同于企业 DLP；生产环境应替换为经过安全团队评审的检测器。

### 5. 三类降级不能混为一句“出错了”

[`SafeFallbackPolicy`](../voice-customer-service-lab/apps/api/src/ai/safe-fallback-policy.ts)
返回结构化决策，而不是把异常消息直接交给 TTS：

| 场景 | 用户侧行为 | 可重试 | 写入记忆 |
| --- | --- | --- | --- |
| 无证据、冲突、过期 | 播放对应的固定证据降级文案 | 否 | 是 |
| 超时、限流、Provider 不可用 | 播放固定“稍后重试”文案 | 是 | 否 |
| 鉴权失败、拒绝、响应非法、未知异常 | 播放固定服务异常文案 | 否 | 否 |
| 用户取消或插话 | 静默结束旧轮次 | 否 | 否 |

取消必须优先判断。否则用户已经插话，旧轮次却又播一句“服务异常”，会形成明显的竞态体验。
所有播报都来自版本化策略，Provider 错误正文、堆栈和凭证不会进入用户响应。

### 6. 离线实验

运行：

```bash
cd voice-customer-service-lab
pnpm inspect:realtime-rag-policy
pnpm test:realtime-rag-policy
```

实验输出应包含：

- `cloud_calls: 0`；
- 固定欢迎语和两份策略的组合版本；
- 4 个 Grounded Prompt 区段，且不打印完整 Prompt；
- `turn_limit`、`token_limit` 和 `excluded_sensitive`；
- `no_evidence`、`provider_unavailable` 和静默 `cancelled` 决策。

测试会覆盖租户隔离、整轮淘汰、敏感排除、快照复制、Locale 失败关闭、Prompt 信任边界、
异常不泄露和取消优先级。

本实验只能证明应用正确组装了策略和上下文，不能证明真实模型一定遵循 Prompt。真实模型的
遵循率需要后续通过安全评测与回归集验证。

### 本节小结与下一步

本节建立的是可复用策略组件，还没有改变现有 `AiOrchestrator`、SSE 或 RTC 运行链路。下一节
会增加 RAG Service，把它们依次接入 Mock、调试 API 和实时语音，同时明确只有完整成功的轮次
才能写入记忆。

## 02 RAG Service 接入 Mock、调试 API 与实时语音

### 本节目标

上一节只有策略组件，本节把它们收进一个可复用的应用服务，并接到三种入口：Mock Voice、
同步调试 API 和 SSE。全程默认使用 Mock LLM 与合成知识，不调用火山、Chroma Cloud 或 RTC。

### 1. 为什么需要统一的 RAG Service？

如果 Mock、HTTP 和 SSE 各自读取记忆、生成 Round ID、处理异常，会很快出现三套不一致的规则。
[`RealtimeRagService`](../voice-customer-service-lab/apps/api/src/ai/realtime-rag-service.ts)
因此统一负责：输入校验、幂等、Session 记忆、Grounded Context、安全降级和清理。

`DefaultAiOrchestrator` 仍然保持无状态，只负责 `Router → Retriever → LLM`。这样以后替换传输层
或模型时，不会复制应用策略。

### 2. 一轮请求如何流动？

```text
服务端 Tenant + 活跃 Session + 用户文本 + Idempotency-Key
  -> RealtimeRagService 读取有界记忆
  -> System + History + 本轮 Question/Evidence
  -> DefaultAiOrchestrator
  -> 校验后的 AiTurnResponse
  -> 完整问答写入记忆
  -> Mock 事件 / HTTP JSON / SSE
```

History 在模型消息中保持独立，只用于理解“那质量问题呢”之类的指代；当前 `EVIDENCE` 才能支持
规则结论。Tenant、Session、Round 和幂等键都不会发给模型。

欢迎语是例外：它在 `session.ready` 后直接变成固定的 AI 事件，不经过检索、模型或记忆。

### 3. 幂等为什么还要覆盖并发？

服务用 `tenantId + sessionId + idempotencyKey` 定位重放记录，并在等待模型前保存正在执行的
Promise：

- 同键同文本的并发请求共享一次模型调用、一个 Round ID 和一次记忆写入；
- 同键不同文本返回 `409 RAG_IDEMPOTENCY_KEY_REUSED`；
- 已完成结果可重放，取消则静默结束并删除未完成记录；
- 敏感或超预算问答不进入记忆，Provider/内部失败也不写入。

课程实现是单进程 Map。多副本生产环境应换成带 TTL 的分布式幂等/单飞存储和加密记忆存储，
但可以保留同一个 Port。

### 4. 三种 Adapter 有什么区别？

| Adapter | 本节做什么 | 不代表什么 |
| --- | --- | --- |
| Mock Voice | 把已校验回答映射成现有标准字幕/音频状态事件 | 不是真实 ASR/TTS，也不能测云端语音延迟 |
| 调试 HTTP | 一次返回答案、引用和执行元数据 | 只在 local/test 且显式开启时可用 |
| 调试 SSE | 先发稳定 Round ID，再分块发送文本和终态 | 文本未进入 RTC，也不是真实模型 Token 流 |

SSE 也必须携带 `Idempotency-Key`。路由在提交 SSE 响应头前先取得 `stream.started`，因此同步的
校验或幂等冲突仍能返回标准 JSON 错误；连接取消后只产生一个 `stream.cancelled`。

Session 正常结束或转人工时，Provider 关闭成功后才清除该 Tenant + Session 的记忆与重放记录；
Provider 关闭失败则保留状态，方便安全重试。已经在执行的旧轮次也会被标记失效，迟到回答不能
把已清理的 Session 记忆重新写回来。

### 5. 零费用实验

运行：

```bash
cd voice-customer-service-lab
pnpm inspect:realtime-rag-service
pnpm test:realtime-rag-service
```

关键输出应为：

```json
{
  "cloud_calls": 0,
  "second_turn_history_messages": 2,
  "replayed": true,
  "stable_round_id": true,
  "memory_before_clear": 2,
  "memory_after_clear": 0
}
```

检查器不会打印完整 Prompt、History、用户文本或证据正文。测试还覆盖并发单飞、跨租户隔离、
固定降级、取消、Mock 事件、HTTP/SSE 契约和关闭清理。

### 6. 当前边界与下一步

现在浏览器通过 Mock 事件看到的确是 RAG 回答，但真实火山 AI Agent 仍走原有托管语音/LLM
路径。本节尚未完成 `ASR → RAG → TTS → RTC`，也没有证明真实弱网下的延迟和打断体验。

下一节会处理多文档流式回答、插话取消和延迟预算：只接收可信 ASR Final，取消旧检索/生成，
再把可播放结果交给 TTS/RTC，同时处理背压和迟到结果。

# 07 Rag 检索增强架构设计

这一章开始从“会调用 LLM API”进入“会设计 AI 应用架构”。

前面学习 LLM API 时，我们主要关心：

```text
如何把用户输入发给模型，再拿到模型回答。
```

但真实业务里，用户经常问的是企业内部资料、课程文档、产品手册、合同、工单、数据库记录等内容。

这些内容模型默认不知道，也不适合为了每次资料更新就重新训练模型。

所以需要 RAG。

RAG 的核心不是“让模型重新学习资料”，而是：

```text
用户提问时，先从外部知识库检索相关资料，
再把资料作为上下文交给大模型生成答案。
```

这一章重点不是背概念，而是建立一个工程视角：

```text
RAG = 数据入库链路 + 检索链路 + 生成链路 + 权限/日志/评估/运维
```

## 01 到底什么 RAG 检索增强？

RAG 的全称是 Retrieval-Augmented Generation，中文通常叫：

```text
检索增强生成
```

拆开来看：

```text
Retrieval = 检索
Augmented = 增强
Generation = 生成
```

所以 RAG 的一句话解释是：

```text
先检索资料，再基于资料生成答案。
```

这里的“增强”不是增强模型参数，而是增强模型回答时看到的上下文。

可以把大模型理解成一个很强的写作和推理引擎，但它未必知道你的私有资料。

RAG 做的事情就是：

```text
把用户问题相关的资料找出来，
放进 Prompt 里，
让模型看着资料回答。
```

### 1. 为什么需要 RAG？

大模型有几个天然限制：

- 不知道企业内部资料。
- 不知道用户自己的私有文件。
- 不一定知道最新变化的信息。
- 可能基于通用知识编出看似合理但实际错误的答案。
- 不能为了每份新文档都重新训练一次模型。

例如用户问：

```text
我们公司今年婚假可以请几天？需要提交什么材料？
```

如果模型没有看到公司制度，它只能凭通用经验回答。

这类回答看起来可能很自然，但不一定符合真实制度。

RAG 的价值就是让模型回答前先看到公司资料：

```text
没有 RAG：模型凭记忆回答
有 RAG：模型查资料后回答
```

### 2. RAG 不是训练模型

很多初学者容易把 RAG 理解成：

```text
把文档喂给模型训练。
```

这个理解不准确。

RAG 通常不改变模型参数。

它做的是：

```text
把文档切分、向量化、存入知识库；
用户提问时，检索相关片段；
把片段放进上下文，让模型基于片段回答。
```

对比一下：

| 方式 | 是否改变模型参数 | 主要解决的问题 |
| --- | --- | --- |
| Prompt | 否 | 临时告诉模型任务和规则 |
| RAG | 否 | 让模型获得外部资料 |
| 微调 | 是 | 改变模型行为、格式、风格或领域能力 |
| 重新训练 | 是 | 从底层学习大规模知识和能力 |

RAG 更像是给模型开卷考试。

资料变了，不需要重新训练模型，只需要更新知识库。

### 3. RAG 的两条主链路

完整 RAG 系统通常分成两条链路：

- 知识库准备链路。
- 用户问答链路。

知识库准备链路：

```text
原始文档
  ↓
文档解析
  ↓
文本清洗
  ↓
文档切分
  ↓
生成 embedding
  ↓
存入向量数据库 / 搜索索引
  ↓
保存元数据和来源信息
```

用户问答链路：

```text
用户问题
  ↓
问题改写 / 意图识别
  ↓
问题向量化
  ↓
检索相关片段
  ↓
过滤 / 重排 / 权限校验
  ↓
组装 Prompt
  ↓
LLM 生成答案
  ↓
返回答案、引用来源、日志记录
```

很多人只看到“向量数据库”，但真正影响效果的是整条链路。

### 4. 一个最小 RAG 架构

一个最小可用 RAG 架构可以这样理解：

```text
用户
  ↓
前端应用
  ↓
业务后端
  ↓
RAG Service
  ├─ 文档库 / 对象存储
  ├─ 向量数据库
  ├─ Embedding 模型
  └─ LLM 模型
```

其中 RAG Service 通常负责：

- 文档入库。
- 文档切分。
- embedding 生成。
- 向量检索。
- Prompt 组装。
- 调用大模型。
- 返回答案和引用来源。

如果是学习项目，可以把这些逻辑放在一个服务里。

如果是企业项目，通常会拆得更清楚。

### 5. RAG 的核心组件

RAG 系统里常见组件包括：

| 组件 | 作用 |
| --- | --- |
| Document Loader | 读取 PDF、Word、网页、Markdown、数据库等资料 |
| Parser | 把原始文件解析成可处理文本 |
| Chunker | 把长文档切成小片段 |
| Embedding Model | 把文本转成语义向量 |
| Vector DB | 存储向量并做相似度检索 |
| Retriever | 根据用户问题找相关片段 |
| Reranker | 对候选片段重新排序，提高相关性 |
| Prompt Builder | 把问题、资料、规则组装成 Prompt |
| LLM | 基于资料生成答案 |
| Citation | 返回答案依据的来源 |
| Evaluator | 评估检索和回答质量 |

这说明 RAG 不是一个单点功能，而是一套应用架构。

### 6. 文档切分为什么重要？

真实文档通常很长，不能全部塞给模型，也不适合整篇文章生成一个向量。

所以要切分成 chunk。

切分太小的问题：

- 上下文不完整。
- 召回的片段缺少前因后果。
- 模型容易答得碎片化。

切分太大的问题：

- 检索不够精准。
- 无关内容进入 Prompt。
- 成本和延迟变高。

一个基本原则是：

```text
chunk 应该尽量保持一个语义单元完整。
```

例如制度文档适合按章节、条款、问答块来切，而不是机械地每 500 个字切一次。

### 7. 检索不等于只用向量

RAG 初学时，经常会把 RAG 简化成：

```text
文档向量化 + 向量数据库搜索。
```

这只是最常见的一种实现方式。

真实项目里还可能组合：

- 关键词检索。
- BM25 稀疏检索。
- 向量语义检索。
- 标签和元数据过滤。
- 权限过滤。
- rerank 重排。
- SQL 查询。
- 图谱查询。

常见工程方案是混合检索：

```text
关键词召回 + 向量召回 + rerank 重排
```

因为向量擅长语义相似，关键词擅长精确匹配。

例如合同编号、产品型号、错误码、法律条款编号这类问题，关键词检索往往很重要。

### 8. RAG 和联网搜索的区别

联网搜索和 RAG 很像，都是先查资料再回答。

但数据来源不同：

```text
联网搜索：查公开互联网。
RAG：查自己的知识库、文件库、数据库。
```

对比：

| 维度 | 联网搜索 | RAG |
| --- | --- | --- |
| 数据来源 | 公开网页 | 私有文档 / 内部系统 / 数据库 |
| 权限控制 | 较弱 | 可以精细控制 |
| 可控性 | 取决于网页质量 | 取决于知识库质量 |
| 更新方式 | 搜索引擎更新 | 自己的数据入库和索引更新 |
| 典型场景 | 新闻、政策、公开资料 | 企业知识库、合同、客服、课程资料 |

真实产品里可以组合使用：

```text
先查内部知识库；
内部没有，再查公开互联网。
```

### 9. RAG 的常见误区

常见误区包括：

- 以为接了向量数据库就等于完成 RAG。
- 以为 RAG 可以彻底消灭幻觉。
- 只关注模型，不关注文档质量。
- 文档切分策略过于粗糙。
- 没有保存来源信息，答案无法追溯。
- 没有做权限过滤，导致资料越权。
- 检索不到资料时仍然强行回答。
- 没有评估集，不知道效果到底好不好。

一个成熟 RAG 系统一定要允许模型说：

```text
根据当前知识库资料，无法回答这个问题。
```

这是可靠性的关键。

## 02 市面主流 AI 应用架构设计解析

理解 RAG 之后，需要把它放进完整 AI 应用架构里。

真实 AI 应用通常不是这样：

```text
前端直接调用大模型 API
```

而是这样：

```text
前端
  ↓
业务后端
  ↓
AI 能力层
  ↓
模型服务 / RAG / 工具 / 数据库
```

核心原因是：

- API Key 不能暴露在前端。
- 需要做用户鉴权和权限控制。
- 需要记录日志和成本。
- 需要限流、重试、缓存。
- 需要管理 Prompt 和模型版本。
- 需要接入业务数据库、知识库和工具系统。

### 1. 架构一：直接调用模型 API

最简单的学习 Demo：

```text
脚本 / 后端服务
  ↓
模型厂商 API
```

优点：

- 上手快。
- 代码少。
- 适合学习模型调用方式。

缺点：

- 不适合复杂业务。
- Prompt、日志、限流、错误处理容易散落。
- 很难统一切换模型。
- 不能承载完整 RAG 流程。

这种架构适合课程前期和小实验。

### 2. 架构二：业务后端封装 LLM 调用

更常见的应用架构：

```text
前端
  ↓
业务后端
  ↓
LLM Client / AI Service
  ↓
模型厂商 API
```

业务后端负责：

- 用户登录态。
- 业务参数校验。
- API Key 管理。
- 模型调用封装。
- 流式输出转发。
- 错误处理。
- 日志记录。

这一步的重点是把模型能力从业务代码里抽出来。

不要让每个页面、每个接口都自己拼 Prompt、自己调模型。

### 3. 架构三：RAG 知识库问答

当应用需要回答私有资料问题时，就要加入 RAG。

典型架构：

```text
前端 Chat UI
  ↓
业务 API
  ↓
Chat Service
  ↓
RAG Service
  ├─ Retriever
  ├─ Prompt Builder
  ├─ LLM Client
  └─ Citation Builder
  ↓
向量数据库 / 文档库 / 元数据数据库
```

一次问答请求可能是这样：

```text
1. 用户发起问题
2. 后端确认用户身份和权限
3. RAG Service 根据问题检索知识库
4. 根据权限过滤不可见文档
5. 对候选片段 rerank
6. 把片段和问题组装成 Prompt
7. 调用 LLM 生成答案
8. 返回答案和引用来源
9. 记录本次检索、Prompt、模型输出和成本
```

这里要特别注意：

```text
权限过滤必须发生在生成答案之前。
```

否则模型可能看到用户不该看到的资料。

### 4. 架构四：Agent + RAG + 工具调用

更复杂的 AI 应用会把 RAG 作为 Agent 的一个工具。

例如企业办公助手：

```text
用户：帮我查一下报销制度，并创建一条报销申请。
```

系统可能需要：

```text
1. 用 RAG 查询报销制度
2. 总结用户需要准备的材料
3. 调用报销系统 API 创建申请
4. 返回申请结果
```

架构上会变成：

```text
用户
  ↓
Agent Orchestrator
  ├─ RAG Tool
  ├─ Database Tool
  ├─ Business API Tool
  └─ LLM
```

RAG 解决的是“查资料”。

Agent 解决的是“为了完成目标，应该调用哪些能力”。

### 5. 企业级 AI 应用常见分层

企业级 AI 应用常见分层可以概括为：

```text
应用层
  ↓
业务服务层
  ↓
AI 编排层
  ↓
数据与工具层
  ↓
模型与基础设施层
```

具体来看：

| 层级 | 典型内容 |
| --- | --- |
| 应用层 | Web、App、后台系统、Chat UI |
| 业务服务层 | 用户、订单、课程、工单、权限、计费 |
| AI 编排层 | Prompt、RAG、Agent、模型路由、工具调用 |
| 数据与工具层 | 文档库、向量库、搜索引擎、数据库、业务 API |
| 模型与基础设施层 | LLM、Embedding、Reranker、GPU、云服务 |

学习阶段不需要一开始就做得很复杂。

但你需要知道真实系统为什么要分层。

分层的目的不是为了画架构图好看，而是为了：

- 控制复杂度。
- 方便替换模型。
- 方便排查问题。
- 方便权限和审计。
- 方便成本治理。
- 方便后续扩展。

### 6. 一个 RAG 系统需要哪些接口？

最小 RAG 后端通常至少有三类接口。

第一类：文档入库接口。

```text
上传文档
解析文档
切分文档
生成 embedding
写入向量库
```

第二类：检索接口。

```text
输入 query
返回相关 chunks
返回 score、source、metadata
```

第三类：问答接口。

```text
输入用户问题
内部完成检索和生成
返回答案、引用来源、检索片段
```

在学习项目里，可以先做问答接口。

在真实项目里，入库、检索、问答最好拆开，方便调试和评估。

### 7. RAG 的核心数据模型

常见数据模型包括：

```text
Document
  id
  title
  source
  type
  owner
  permission
  createdAt
  updatedAt

Chunk
  id
  documentId
  content
  index
  tokenCount
  metadata

Embedding
  chunkId
  vector
  model
  dimension

ChatLog
  userId
  question
  retrievedChunkIds
  answer
  model
  cost
  latency
```

如果没有这些结构，后续会很难排查：

- 为什么答错了？
- 查到了哪些片段？
- 是检索错了，还是模型生成错了？
- 用户有没有权限看到这些资料？
- 哪个模型版本效果更好？

RAG 工程不是只追求“能回答”，还要追求“能解释为什么这么回答”。

### 8. 如何判断一个 RAG 架构是否靠谱？

可以用下面几个问题检查：

- 数据来源是否清楚？
- 文档解析是否稳定？
- chunk 是否保留来源和上下文？
- 检索结果是否可查看？
- 是否支持找不到资料时拒答？
- 是否返回引用来源？
- 是否有权限过滤？
- 是否记录日志？
- 是否能评估召回率和答案质量？
- 是否能替换 embedding、reranker 和 LLM？

如果这些问题都回答不上来，说明系统还只是 Demo，不是可长期运行的产品架构。

## 03 为什么现在云服务是主流趋势？

AI 应用里，“云服务”变成主流，不只是因为大家喜欢用云。

而是因为大模型相关能力背后需要大量复杂基础设施。

包括：

- GPU 资源。
- 模型部署。
- 推理加速。
- 弹性扩缩容。
- 多模型版本管理。
- API 鉴权和限流。
- 日志和监控。
- 数据安全和合规。
- Embedding、Reranker、语音、图片等配套能力。

对于大多数团队来说，直接使用成熟云服务比自建全套基础设施更现实。

### 1. 模型推理成本很高

传统 Web 服务主要消耗 CPU、内存和数据库。

大模型推理通常还需要 GPU 或专门推理芯片。

如果自己部署，需要考虑：

- GPU 采购和维护。
- 显存容量。
- 推理框架。
- 并发调度。
- 模型量化。
- 服务稳定性。
- 峰值流量扩容。

这些事情对学习者和普通业务团队都很重。

云服务把这些复杂度封装成 API：

```text
业务代码调用 API，
云厂商负责模型部署和推理资源。
```

### 2. 模型迭代太快

大模型能力变化很快。

如果所有模型都自建部署，团队要不断处理：

- 新模型适配。
- 旧模型下线。
- 推理框架升级。
- 显存和吞吐优化。
- API 能力变化。

使用云服务时，团队可以更快试用新模型。

但是这也带来一个架构要求：

```text
业务代码不要和某一个模型厂商强绑定。
```

更好的做法是封装一层 LLM Client 或 AI Gateway。

这样未来从 A 模型切到 B 模型，不需要重写所有业务代码。

### 3. 云服务让团队先关注业务闭环

学习和创业阶段，最重要的是先验证：

- 用户是不是真的需要这个功能？
- RAG 是否能查到正确资料？
- 答案是否足够可靠？
- 成本是否能接受？
- 交互体验是否顺畅？

如果一开始就自建模型部署，很容易把精力耗在基础设施上。

更合理的路径是：

```text
先用云 API 跑通业务闭环；
当规模、成本、合规要求明确后，再考虑私有化或自部署。
```

### 4. 云服务不等于没有架构

使用云服务时，很多人会误以为架构很简单：

```text
直接调模型 API 就行。
```

这在 Demo 阶段可以。

但在真实项目里，仍然需要自己的后端架构。

因为你还要负责：

- 用户体系。
- 权限控制。
- 业务数据。
- Prompt 版本。
- 知识库更新。
- 成本统计。
- 日志审计。
- 错误重试。
- 模型降级。
- 输出安全。

云服务解决的是模型基础设施问题。

业务系统仍然需要自己设计。

### 5. 什么时候考虑自部署？

云服务是主流，但不是唯一答案。

以下场景可以考虑自部署或私有化：

- 数据极度敏感，不能出内网。
- 调用量非常大，云 API 成本过高。
- 对延迟、可用区、网络有特殊要求。
- 需要深度控制模型、推理参数和部署环境。
- 公司已有 GPU 集群和模型工程团队。
- 合规要求必须本地化部署。

但要注意：

```text
自部署不是免费。
它只是把 API 成本换成了硬件、运维、工程和人力成本。
```

### 6. 更推荐的工程姿势

学习和中小项目推荐这样做：

```text
业务后端
  ↓
统一 AI Service
  ↓
模型供应商 / 云服务
```

AI Service 负责：

- 封装不同模型接口。
- 统一流式输出。
- 管理 Prompt 模板。
- 记录请求日志。
- 统计 token 和成本。
- 提供 RAG 检索能力。
- 做模型降级和重试。

不要让业务代码到处直接调用不同模型。

也不要让前端直接调用模型 API。

### 7. 本章小结

这一章要建立三个核心认知。

第一，RAG 不是训练模型。

```text
RAG 是把外部资料检索出来，放进上下文，让模型基于资料回答。
```

第二，RAG 是一套架构。

```text
它包含文档入库、切分、向量化、检索、重排、Prompt、生成、引用、权限和评估。
```

第三，云服务是当前 AI 应用的主流基础设施。

```text
云服务帮我们降低模型部署和推理门槛，
但业务架构、RAG 质量和数据治理仍然需要自己设计。
```

用一句话总结：

```text
会调用模型 API 只是入口；
会设计 RAG 架构，才开始进入真正的 AI 应用工程。
```

### 3. 分析一次 RAG 错误

假设用户问：

```text
公司婚假需要提交什么材料？
```

系统回答错了。

请判断可能是哪一层出问题：

- 文档没有入库。
- 文档切分不合理。
- embedding 效果不好。
- 检索没有召回正确片段。
- rerank 排序错误。
- Prompt 没有约束模型基于资料回答。
- 模型生成时忽略了资料。
- 用户没有权限看到正确资料。

真实项目排查 RAG 问题时，就要沿着这条链路逐层定位。

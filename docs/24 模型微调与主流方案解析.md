## 01 SFT 和 DPO 的区别？

### 本节目标

学完这一节，应该能够：

- 分别解释 SFT 和 DPO 在训练模型学习什么；
- 区分“标准答案数据”和“偏好对比数据”；
- 看懂 SFT 与 DPO 的基本训练目标；
- 解释 DPO 为什么不需要单独训练奖励模型，却仍需要参考模型；
- 判断一个业务需求应该先用 SFT、DPO，还是两者组合；
- 判断企业需求应该使用提示词、RAG、工具调用还是微调；
- 从数据、训练、评测、部署和调用量分析微调成本；
- 解释模型能力提高、API 降价后微调价值会怎样变化；
- 识别“DPO 可以完全替代 SFT”等常见误区。

本节主要依据 [InstructGPT 论文](https://arxiv.org/abs/2203.02155)、
[DPO 原始论文](https://arxiv.org/abs/2305.18290)以及 Hugging Face TRL 的
[SFTTrainer](https://huggingface.co/docs/trl/en/sft_trainer)和
[DPOTrainer](https://huggingface.co/docs/trl/en/dpo_trainer)文档整理。

### 1. 先用一句话区分

先记住最核心的区别：

```text
SFT：给模型一个理想答案，让模型模仿“应该怎样回答”。

DPO：给模型同一问题下的一好一坏两个答案，让模型学习“更应该偏好哪一个”。
```

例如用户问：

```text
刚收到手机，发现屏幕碎了，应该怎么处理？
```

SFT 数据直接提供一个理想客服回答；DPO 数据则同时提供两个候选回答，并标明哪个更好：

```text
SFT：问题 → 理想回答

DPO：问题 → chosen（更优回答） + rejected（较差回答）
```

两者都属于后训练（post-training）方法，都会更新模型参数，但监督信号不同：SFT 的信号是
“目标文本是什么”，DPO 的信号是“两个回答谁更符合偏好”。

### 2. SFT：从标准示范中学习

SFT 是 **Supervised Fine-Tuning**，中文通常称为“监督微调”。它使用人工编写、人工审核或由
高质量模型生成并过滤的示范数据训练模型。

一个聊天格式的 SFT 样本可以写成：

```json
{
  "messages": [
    {
      "role": "user",
      "content": "刚收到手机，发现屏幕碎了，应该怎么处理？"
    },
    {
      "role": "assistant",
      "content": "很抱歉影响了你的收货体验。请先停止使用并保留包装，拍摄外包装、快递面单和屏幕破损照片，然后在订单页面申请退换货；如果入口不可用，请联系平台客服并提供订单号。"
    }
  ]
}
```

训练过程中，模型看到问题和已经写好的目标回答，并学习逐个预测目标回答中的 token。它适合学习：

- 指令与输出格式，例如“只返回 JSON”；
- 新的业务任务，例如把客服对话分类到工单类型；
- 领域表达和处理流程，例如企业售后规则；
- 对话角色与语气，例如简洁、专业、先结论后说明；
- 工具调用示范，例如在什么情况下调用订单查询接口。

可以把 SFT 理解为老师直接演示一道题的完整解法。示范的内容、格式和错误都会被模型模仿，因此
一条高质量示范通常要同时满足正确、完整、相关和风格一致。

SFT 并不是把资料原封不动存进模型，也不能保证模型精确记住所有新事实。频繁变化或必须精确
查询的信息仍更适合放在数据库、API 或 RAG 知识库中；SFT 更适合调整模型的行为模式和任务能力。

### 3. DPO：从相对偏好中学习

DPO 是 **Direct Preference Optimization**，中文常称为“直接偏好优化”。一条数据包含同一个
提示下的优选回答 `chosen` 和非优选回答 `rejected`：

```json
{
  "prompt": [
    {
      "role": "user",
      "content": "刚收到手机，发现屏幕碎了，应该怎么处理？"
    }
  ],
  "chosen": [
    {
      "role": "assistant",
      "content": "很抱歉影响了你的收货体验。请停止使用并保留包装，拍摄外包装、快递面单和屏幕破损照片，然后在订单页面申请退换货；如入口不可用，请联系平台客服并提供订单号。"
    }
  ],
  "rejected": [
    {
      "role": "assistant",
      "content": "拍张照片联系客服就行。"
    }
  ]
}
```

两个回答不一定是“完全正确”和“完全错误”。这里的 `rejected` 也给出了大致方向，但缺少停止
使用、保留包装、证据范围和具体操作入口。DPO 要学习的是这种相对差异：在同一个问题下，完整、
可执行且符合客服规范的回答更值得选择。

DPO 适合调整：

- 回答的有用性、完整性和礼貌程度；
- 简洁与详细之间的业务偏好；
- 安全拒答边界；
- 摘要、翻译或写作结果的相对质量；
- 多个基本可用答案之间的风格和质量排序。

原始 DPO 方法由传统 RLHF 目标推导而来，但训练时直接使用偏好对做分类式优化，不需要先训练一个
显式奖励模型，也不需要在微调循环中使用 PPO 反复采样和强化学习。这正是“Direct”的含义。

不过，DPO 通常仍要保留一个冻结的参考模型，或者预先计算参考模型对数据的对数概率，用来限制
训练后的模型不要为了迎合偏好数据而偏离原模型过远。

### 4. 同一个需求，两种数据怎样配合？

假设要训练一个电商售后助手。原始基础模型可能存在三个阶段的问题：

| 模型状态 | 典型问题 | 更适合的手段 |
| --- | --- | --- |
| 不会按客服流程回答 | 不知道先核验订单、保留凭证、给出入口 | SFT |
| 已经会回答，但风格不稳定 | 有时啰嗦，有时遗漏关键风险提示 | DPO |
| 回答看起来不错，但事实可能错误 | 编造退款时效或不存在的规则 | 业务数据校验、RAG、评测，不能只靠 DPO |

SFT 数据告诉模型“一个合格售后回答由哪些步骤构成”：

```text
用户问题
  ↓
道歉与确认问题
  ↓
给出安全提醒和证据要求
  ↓
说明订单页面操作步骤
  ↓
提供无法自助处理时的升级路径
```

DPO 数据在模型已经能生成候选回答后，进一步表达偏好：

```text
同一个用户问题
  ├─ 回答 A：准确、完整、可执行 → chosen
  └─ 回答 B：方向没错但遗漏关键步骤 → rejected
```

因此，SFT 更像“教会基本动作”，DPO 更像“在多个会做的动作中校准选择倾向”。这只是帮助理解
的工程直觉，不表示 DPO 只能改变风格；只要偏好数据持续表达某种判断标准，DPO 就可能强化相应
行为。但它学到的是数据中实际体现的偏好，而不是标注者没有表达出来的抽象价值观。

### 5. 训练目标到底有什么不同？

先看 SFT。设输入提示为 $x$，理想回答为 $y^*$，模型为 $\pi_\theta$。简化后的损失为：

$$
\mathcal{L}_{\mathrm{SFT}}(\theta)
=
-\mathbb{E}_{(x,y^*)}
\left[
\sum_t \log \pi_\theta(y_t^* \mid x, y_{<t}^*)
\right]
$$

不必死记公式，先理解它表达的动作：

```text
让模型提高“标准回答中每个正确 token”的生成概率。
```

SFT 只有目标回答，没有在同一条样本里明确告诉模型“另一个回答为什么更差”。

DPO 的一条数据为 $(x, y^+, y^-)$，分别表示提示、优选回答和非优选回答。原始 DPO 损失为：

$$
\mathcal{L}_{\mathrm{DPO}}(\theta)
=
-\mathbb{E}
\left[
\log \sigma
\left(
\beta
\left[
\log \frac{\pi_\theta(y^+ \mid x)}{\pi_{\mathrm{ref}}(y^+ \mid x)}
-
\log \frac{\pi_\theta(y^- \mid x)}{\pi_{\mathrm{ref}}(y^- \mid x)}
\right]
\right)
\right]
$$

其中：

| 符号 | 含义 |
| --- | --- |
| $y^+$ | `chosen`，更受偏好的回答 |
| $y^-$ | `rejected`，相对较差的回答 |
| $\pi_\theta$ | 正在训练的策略模型 |
| $\pi_{\mathrm{ref}}$ | 冻结的参考模型 |
| $\sigma$ | Sigmoid 函数，把差值映射为偏好概率 |
| $\beta$ | 控制相对参考模型偏离程度的超参数 |

直觉上，DPO 关心的不是单独把 `chosen` 背下来，而是相对参考模型扩大 `chosen` 与 `rejected` 的
优势差距：

```text
训练目标：chosen 的相对优势 > rejected 的相对优势
```

在常见 TRL 实现中，更高的 $\beta$ 通常意味着对偏离参考模型施加更强约束。参数的具体影响还与
损失实现有关，后续讲解 DPO 训练参数时再展开。

### 6. 为什么常见流程是先 SFT，再 DPO？

一个经典的后训练流程是：

```text
预训练基础模型
  ↓
SFT：学习指令、任务和标准回答格式
  ↓
生成多个候选回答并收集人类偏好
  ↓
DPO：让模型更倾向 chosen、远离 rejected
  ↓
独立评测与安全测试
```

[InstructGPT 论文](https://arxiv.org/abs/2203.02155)采用了“先用人工示范做 SFT，再收集输出排序
进行偏好对齐”的思路；它的偏好阶段使用奖励模型与 PPO，而 DPO 后来提供了一条不显式训练奖励
模型的简化路线。[DPO 原始论文](https://arxiv.org/abs/2305.18290)则从 KL 约束的 RLHF 目标推导出
直接使用偏好对训练策略的方法。

先做 SFT 的实际原因包括：

1. 基础模型需要先学会对话格式和基本任务，才能生成值得比较的候选答案；
2. 质量接近但存在关键差别的答案对，通常比“一眼就错”的答案对提供更有价值的偏好信号；
3. SFT 检查点可以同时作为 DPO 的初始模型和参考模型来源；
4. 团队可以先分别定位“能力不会”还是“选择偏好不对”，减少问题混在一起。

这不是不可违反的定律。如果起点已经是能力足够的指令模型，而且手里有高质量偏好对，可以直接
做 DPO；如果业务只有高质量标准答案、没有可靠的成对偏好，就先做 SFT。是否组合取决于模型起点、
数据类型和评测结果。

### 7. 核心对照、企业决策与发展趋势

| 对比维度 | SFT | DPO |
| --- | --- | --- |
| 全称 | Supervised Fine-Tuning | Direct Preference Optimization |
| 每条数据 | 提示 + 理想回答 | 提示 + chosen + rejected |
| 核心问题 | 应该生成什么？ | 两个回答更偏好哪个？ |
| 主要目标 | 提高目标回答 token 的概率 | 扩大优选与非优选回答的相对差距 |
| 是否需要参考模型 | 通常不需要 | 原始方法需要参考模型或其预计算概率 |
| 是否需要显式奖励模型 | 不需要 | 不需要 |
| 是否需要 PPO 在线采样循环 | 不需要 | 不需要 |
| 常见用途 | 学任务、格式、领域流程 | 调风格、质量、安全与行为偏好 |
| 单步训练成本 | 通常较低 | 同时处理两段回答和参考概率，通常高于同规模 SFT |
| 典型位置 | 后训练的基础阶段 | SFT 之后的偏好对齐阶段 |

需要特别纠正五个误区：

1. **“DPO 比 SFT 新，所以可以完全替代 SFT。”**

   两者解决的问题不同。没有偏好对时无法直接做标准 DPO；基础能力不足时，先做 SFT 往往更稳妥。
2. **“DPO 不需要奖励模型，所以不需要参考模型。”**

   原始 DPO 不训练显式奖励模型，但损失中仍使用参考策略 $\pi_{\mathrm{ref}}$。
3. **“DPO 就是把 chosen 当成 SFT 答案训练。”**

   DPO 同时比较 chosen、rejected 及其相对参考模型的概率，目标不是普通的单答案最大似然。
4. **“rejected 越差，训练效果越好。”**

   过于荒谬的负例很容易区分，却未必能教会模型细微的质量边界；高价值偏好对通常具有可比较性。
5. **“训练 loss 降低就代表模型更好。”**

   SFT loss 和 DPO preference accuracy 都只是训练信号，还要在未参与训练的数据上评估正确性、
   任务成功率、人类偏好、安全性以及是否损伤原有能力。

**企业为什么还需要微调？**

微调有用，但不是企业使用大模型的默认步骤。提示词、RAG、工具调用和微调分别解决不同问题：

| 方法 | 改变什么 | 最适合解决 |
| --- | --- | --- |
| 提示词 | 本次请求中的指令和上下文 | 临时角色、语气、简单格式和少量示例 |
| RAG | 给模型补充当前外部资料 | 企业文档、产品信息和经常变化的知识 |
| 工具调用 | 让模型访问或操作外部系统 | 查询订单、读取数据库、计算和执行业务动作 |
| 微调 | 持久调整模型参数中的行为倾向 | 固定任务、稳定格式、领域流程、工具选择和回答偏好 |

因此，“让模型知道最新商品库存”应使用数据库或 RAG；“让模型稳定地把售后请求分成企业定义的
12 类工单”才可能适合 SFT。可以用下面的顺序做企业决策：

```text
建立真实业务评测集
  ↓
先测试强基础模型与提示词
  ↓
需要外部事实时接入 RAG / 数据库 / 工具
  ↓
仍存在重复、系统性的行为错误
  ↓
再评估 SFT、DPO 或小模型蒸馏
```

Hugging Face 的 [PEFT 方法选择指南](https://huggingface.co/docs/peft/main/methods/overview)也建议先
确认提示方法是否已经可以完成任务，不足时再采用适配器等参数高效微调方法，并检查模型是否遗忘
原有能力。

企业中常见的微调场景包括：

- 高频分类、抽取、审核、路由和固定格式生成；
- 稳定执行企业特有的客服、工单或工具调用流程；
- 让小模型承担大量窄任务，替代更昂贵的大模型调用；
- 私有化、离线、端侧或严格数据边界中的模型适配；
- 通过 DPO 等方法调整有用性、简洁程度、安全边界和品牌偏好。

普通企业应用中，SFT + LoRA 通常比 DPO 更容易落地，因为前者只需要高质量标准答案，后者还要
为同一个问题准备可比较的 `chosen/rejected` 并建立一致的偏好规范。没有可靠的跨行业公开统计
可以证明“多数企业都会微调”，所以更客观的说法是：微调已经是主流云平台和模型工具链提供的标准
能力，但只在能够证明业务收益的项目中使用。Amazon Bedrock 目前同时提供
[监督微调、强化微调和蒸馏](https://docs.aws.amazon.com/bedrock/latest/userguide/custom-models.html)，
并把训练数据、验证数据、训练指标、权限和存储纳入模型定制流程。

**微调成本不能只看一次训练用了多少 GPU。**

完整成本应写成：

```text
总成本
= 数据收集与脱敏
+ 专家编写、标注和清洗
+ GPU 或托管训练
+ 多轮参数实验
+ 独立评测与安全测试
+ 模型存储和部署
+ 持续推理
+ 数据漂移后的维护与重训
```

其中，数据和人员成本经常比一次 LoRA 训练更高。500 条覆盖真实边界、经过专家审核的数据，可能
比 50,000 条规则不一致的合成数据更有价值。不同方案的成本特征为：

| 方案 | 训练成本 | 额外成本与风险 |
| --- | --- | --- |
| 托管 API 微调 | 按 token 或训练小时付费，不维护 GPU | 受模型支持、版本退役和供应商价格影响 |
| LoRA | 只更新少量适配器参数，显存和存储压力较低 | 仍需加载基础模型并维护适配器版本 |
| QLoRA | 量化基础模型，进一步降低基础模型显存 | 训练速度、量化方案和质量需要实测 |
| 全参数微调 | 更新全部权重，通常需要多张高显存 GPU | 训练、检查点、部署和遗忘风险都更高 |
| DPO | 同时处理 chosen、rejected 和参考概率 | 偏好数据制作更贵，训练通常重于同规模 SFT |

参数高效不等于完全不占显存。Hugging Face 的
[训练内存说明](https://huggingface.co/docs/peft/main/developer_guides/memory_efficient_training)指出，
完整训练还涉及基础模型权重、梯度、优化器状态和中间激活；LoRA 主要减少可训练参数对应的梯度与
优化器状态，而批量大小、序列长度和激活仍会影响内存。

托管价格会随模型、区域和日期变化。截至 2026-08-06，Amazon Bedrock 给出的一个强化微调实例是
Qwen3 32B 每训练小时 80 美元，另收模型存储和推理 token 费用。它只是一个当前 RFT 报价示例，
不能当作 LoRA、SFT 或其他平台的统一价格，实际预算必须以选定平台的
[最新价格页](https://aws.amazon.com/bedrock/pricing/)和小规模实测为准。

真正判断“值不值得”的方法是计算盈亏平衡调用量：

```text
盈亏平衡调用量
= 微调、评测和部署的固定成本
  ÷（强模型单次调用成本 - 微调小模型单次调用成本）
```

例如固定投入为 100,000 元，强模型每次调用 0.05 元，微调小模型每次 0.005 元，则理论盈亏平衡点
约为：

```text
100,000 ÷ (0.05 - 0.005) ≈ 222 万次调用
```

这只是展示计算方法。还应把并发、GPU 空闲时间、人工运维、错误造成的业务损失以及模型升级后的
重训成本加入真实预算。

**随着模型能力提高和价格下降，微调是不是越来越没有必要？**

如果“微调”特指普通企业自己给一个强大的通用模型做 SFT 或 DPO，答案是：**必要性确实在下降**。
更强的指令遵循、结构化输出、长上下文、RAG 和工具调用，正在替代许多过去需要微调的需求；API
价格下降还会缩小“大模型调用”与“自建微调模型”之间的单次成本差，使上面的盈亏平衡点变得更高。

但如果“微调”指广义的模型后训练和专项优化，答案是：**不会消失，而是在转移用途**。

| 场景 | 微调必要性趋势 | 主要原因 |
| --- | --- | --- |
| 通用聊天、简单语气与格式 | 下降 | 强模型、提示词和结构化输出已经足够 |
| 企业知识问答 | 下降 | 动态知识更适合 RAG，而不是写入参数 |
| 低流量普通应用 | 下降 | 微调固定成本更难摊薄 |
| 高频分类、抽取和路由 | 仍有价值 | 专项小模型可能更便宜、更快、更稳定 |
| 私有化、端侧和离线部署 | 仍然重要 | 不能完全依赖外部强模型 API |
| 小模型替代大模型 | 可能增加 | 蒸馏与 LoRA 可以降低长期推理成本 |
| 模型厂商的指令、安全和偏好后训练 | 长期必要 | 预训练模型仍需被塑造成可用产品 |
| 普通企业自行做 DPO | 相对小众 | 偏好数据与评测门槛高于普通 SFT |

同时，微调本身也在因为 LoRA、QLoRA、合成数据和托管训练而变便宜。因此未来更可能出现分化：

```text
复杂、低频、变化快的任务
  → 直接调用更强的通用模型 + RAG / 工具

简单、高频、边界稳定的任务
  → 微调或蒸馏一个更小的专项模型
```

所以，微调从“所有大模型应用都应该尝试的默认步骤”，转向“只有通过评测和成本模型证明值得时
才采用的专项工程手段”。对应用企业，它的普遍必要性在下降；对小模型专项化、私有部署和模型厂商
后训练，它仍然具有长期价值。

### 本节练习

判断下面的需求更适合 SFT、DPO，还是两者组合：

1. 模型必须把工单稳定输出为指定 JSON Schema；
2. 模型已经能写摘要，但经常过长，希望它更偏好简洁且不遗漏事实的版本；
3. 基础模型不会公司售后流程，同时回答语气也不符合品牌要求；
4. 手中只有 5,000 条人工编写的高质量问答，没有 rejected 回答；
5. 手中有同一问题下的两份回答，以及经过统一规范审核的偏好结果；
6. 商品价格每天变化，希望模型永远回答最新价格；
7. 每年有一亿次固定工单分类请求，强模型效果好但单次成本较高；
8. 低流量内部工具通过系统提示词已经达到评测目标。

参考判断：

| 题号 | 建议 | 原因 |
| --- | --- | --- |
| 1 | SFT | 直接示范固定输出结构 |
| 2 | DPO | 已具备能力，重点是相对风格和质量偏好 |
| 3 | 先 SFT，再视评测做 DPO | 先补任务能力，再校准品牌偏好 |
| 4 | SFT | 数据是标准示范，不是偏好对 |
| 5 | DPO | 数据天然包含 chosen 与 rejected |
| 6 | RAG、数据库或 API | 动态事实不应依靠模型参数记忆 |
| 7 | 评估 SFT + LoRA 小模型 | 高频调用可能摊薄固定训练成本 |
| 8 | 不微调 | 当前方案已达到目标，微调只会增加成本和风险 |

最后用自己的话补全：

```text
SFT 用 __________ 数据，主要让模型学习 __________。
DPO 用 __________ 数据，主要让模型学习 __________。
```

参考答案：SFT 使用提示与理想回答数据，学习怎样完成任务；DPO 使用同一提示下的优选与非优选
回答对，学习更偏好哪一种行为。

### 本节小结

本节可以浓缩为下面一张路线图：

```text
模型还不会按要求完成任务
  ↓
SFT：用理想示范教“怎样回答”
  ↓
模型已经能生成多个基本可用的回答
  ↓
DPO：用 chosen / rejected 教“更偏好哪个”
  ↓
在独立数据上评估任务能力、偏好和安全性
```

SFT 的核心是模仿目标回答，DPO 的核心是学习相对偏好。DPO 简化了传统偏好对齐中的显式奖励
模型与 PPO 环节，但没有消除对高质量标注、参考策略和独立评测的需要。工程中最常见的思路不是
“二选一”，而是先用评测判断模型当前缺少的是基础能力还是偏好校准，再选择提示词、RAG、工具、
SFT、DPO 或组合方案。

随着强模型能力提高和价格下降，普通应用直接微调强模型的必要性正在降低；但高频窄任务的小模型
微调、私有部署以及模型厂商的后训练仍会长期存在。是否微调最终不是技术潮流判断，而是一道可以
用质量提升、调用规模、固定投入和长期运维共同计算的工程经济题。

## 02 SFT 的两种主流训练数据格式

### 本节目标

学完这一节，应该能够：

- 区分 Alpaca 风格与 ShareGPT/OpenAI 风格的 SFT 数据；
- 解释 `instruction`、`input`、`output` 和 `messages` 中各字段的作用；
- 为单轮任务和多轮对话选择合适的数据结构；
- 在 LLaMA-Factory 的 `dataset_info.json` 中声明格式与字段映射；
- 解释聊天模板怎样把结构化消息转换成模型真正看到的 token；
- 区分 JSON、JSONL 文件封装与 SFT 训练语义；
- 检查角色顺序、空回答、字段漂移和训练目标泄漏等常见问题。

本节以 [LLaMA-Factory 官方数据格式说明](https://github.com/hiyouga/LlamaFactory/blob/main/data/README.md)
为主要依据。官方目前支持 `alpaca` 和 `sharegpt` 两种格式，并把 OpenAI 的 `messages` 格式视为
ShareGPT 的一个特例。作为对照，Hugging Face TRL 将数据分成标准文本与会话消息两类结构，并支持
语言建模和 prompt-completion 两种任务类型，见
[TRL Dataset Formats](https://huggingface.co/docs/trl/dataset_formats)。

### 1. 先区分训练语义与文件封装

“SFT 数据格式”经常混合了两个不同层次的问题。

第一层是**一条样本表达什么**：

```text
Alpaca 风格
  instruction + input → output

ShareGPT / OpenAI 风格
  system / user / assistant / tool 等消息序列
```

第二层是**许多样本怎样保存在文件中**：

```text
JSON：整个文件通常是一个数组
JSONL：每一行是一个独立 JSON 对象
```

所以，JSON 与 JSONL 不是第三、第四种 SFT 训练语义。同一份 Alpaca 或 ShareGPT 数据都可以保存成
JSON、JSONL，甚至由框架从 Parquet、Arrow 或数据集服务读取。

训练框架最终还会把字段转换成统一过程：

```text
原始 JSON / JSONL
  ↓
字段映射
  ↓
构造 system、user、assistant 消息
  ↓
应用目标模型的 chat template
  ↓
分词得到 input_ids
  ↓
创建 labels 和 loss mask
  ↓
执行 SFT
```

因此，字段名称不是模型直接理解的内容。模型最终看到的是聊天模板产生的 token 序列。

### 2. Alpaca：指令、输入与标准输出

Alpaca 风格适合结构明确的单轮任务。一条典型数据包含：

```json
[
  {
    "instruction": "判断下面电商评论的整体情绪，只输出 positive、negative 或 mixed。",
    "input": "包装破损，好在商品本身没问题。",
    "output": "mixed",
    "system": "你是一个严格遵守标签定义的电商评论分类器。"
  }
]
```

字段含义如下：

| 字段 | 是否必需 | 作用 |
| --- | --- | --- |
| `instruction` | 是 | 描述模型要完成的任务 |
| `input` | 否 | 本条样本的具体输入、上下文或待处理数据 |
| `output` | 是 | 希望模型学习生成的标准回答 |
| `system` | 否 | 全局角色、规则或行为约束 |
| `history` | 否 | 当前轮次之前的用户—助手历史对话 |

在 LLaMA-Factory 中，`instruction` 和 `input` 会拼接成当前用户提示，`output` 是模型回答。为了让
任务边界更清楚，可以遵循：

```text
instruction：跨样本相对稳定的任务要求
input：每条样本变化的业务内容
output：模型应该生成的结果
```

例如信息抽取任务：

```json
[
  {
    "instruction": "提取订单号和问题类型，返回 JSON。",
    "input": "订单 A20260806001 收到后屏幕破损。",
    "output": "{\"order_id\":\"A20260806001\",\"issue_type\":\"damaged\"}"
  },
  {
    "instruction": "提取订单号和问题类型，返回 JSON。",
    "input": "订单 A20260806002 至今没有发货。",
    "output": "{\"order_id\":\"A20260806002\",\"issue_type\":\"not_shipped\"}"
  }
]
```

注意，外层 `output` 本身是 JSON 字符串，所以内部双引号必须转义。模型学习生成的内容是：

```json
{"order_id":"A20260806001","issue_type":"damaged"}
```

Alpaca 也可以使用 `history` 表示简单多轮上下文：

```json
[
  {
    "instruction": "继续回答用户的问题。",
    "input": "需要支付退货运费吗？",
    "output": "如果确认属于到货破损，通常应按平台规则由商家承担；请以订单售后页面显示为准。",
    "history": [
      [
        "我刚收到手机，发现屏幕碎了。",
        "请停止使用并保留包装，拍照后从订单页面申请退换货。"
      ]
    ]
  }
]
```

LLaMA-Factory 官方说明中，`history` 里的历史助手回答也会参与 SFT 学习。如果对角色、多轮顺序或
工具调用有更复杂的要求，ShareGPT 结构通常更直观。

### 3. ShareGPT 与 OpenAI：用消息表示对话

ShareGPT 风格把对话表示为有序消息列表，适合多轮聊天、工具调用和多角色数据。LLaMA-Factory 的
原生 ShareGPT 结构使用 `conversations/from/value`：

```json
[
  {
    "conversations": [
      {
        "from": "human",
        "value": "我刚收到手机，发现屏幕碎了。"
      },
      {
        "from": "gpt",
        "value": "请停止使用并保留包装，拍照后从订单页面申请退换货。"
      },
      {
        "from": "human",
        "value": "需要支付退货运费吗？"
      },
      {
        "from": "gpt",
        "value": "如果确认属于到货破损，通常应按平台规则由商家承担；请以订单售后页面显示为准。"
      }
    ],
    "system": "你是一个谨慎、准确的电商售后助手。"
  }
]
```

常见角色为：

| ShareGPT 角色 | 含义 | 是否通常作为模型目标 |
| --- | --- | --- |
| `human` | 用户输入 | 否 |
| `gpt` | 助手回答 | 是 |
| `observation` | 工具执行结果 | 否 |
| `function_call` | 模型生成的工具调用参数 | 是 |

官方要求消息符合合理的轮次顺序：`human` 或 `observation` 提供输入，`gpt` 或 `function_call`
提供模型要学习的输出。如果两个 `human` 连续出现，或样本最后只有用户问题没有助手目标，框架可能
拒绝样本，也可能产生与预期不一致的训练序列。

许多 API、标注工具和数据集使用更通用的 OpenAI 消息结构：

```json
[
  {
    "messages": [
      {
        "role": "system",
        "content": "你是一个谨慎、准确的电商售后助手。"
      },
      {
        "role": "user",
        "content": "我刚收到手机，发现屏幕碎了。"
      },
      {
        "role": "assistant",
        "content": "请停止使用并保留包装，拍照后从订单页面申请退换货。"
      }
    ]
  }
]
```

它与 ShareGPT 的训练语义相同，主要是字段和角色名称不同：

| ShareGPT | OpenAI messages |
| --- | --- |
| `conversations` | `messages` |
| `from` | `role` |
| `value` | `content` |
| `human` | `user` |
| `gpt` | `assistant` |

因此本节把它们归为同一类“会话消息格式”，而不是把 OpenAI 格式算作第三种独立的 SFT 语义。

### 4. 在 LLaMA-Factory 中声明字段映射

训练文件放入 LLaMA-Factory 的数据目录后，还需要在 `dataset_info.json` 注册。即使字段使用默认
名称，显式写出映射也有利于检查和迁移。

Alpaca 数据可以配置为：

```json
{
  "ecommerce_alpaca_sft": {
    "file_name": "ecommerce-alpaca-sft.json",
    "formatting": "alpaca",
    "columns": {
      "prompt": "instruction",
      "query": "input",
      "response": "output",
      "system": "system",
      "history": "history"
    }
  }
}
```

这里 `prompt/query/response` 是 LLaMA-Factory 内部理解的语义角色，右侧才是当前文件里的真实字段名。
如果原始数据使用 `question/context/answer`，不必重写全部数据，只需改变右侧映射：

```json
{
  "columns": {
    "prompt": "question",
    "query": "context",
    "response": "answer"
  }
}
```

原生 ShareGPT 数据可以配置为：

```json
{
  "ecommerce_sharegpt_sft": {
    "file_name": "ecommerce-sharegpt-sft.json",
    "formatting": "sharegpt",
    "columns": {
      "messages": "conversations",
      "system": "system"
    }
  }
}
```

如果文件使用 OpenAI 的 `messages/role/content`，则同时映射消息字段与角色标签：

```json
{
  "ecommerce_messages_sft": {
    "file_name": "ecommerce-messages-sft.jsonl",
    "formatting": "sharegpt",
    "columns": {
      "messages": "messages"
    },
    "tags": {
      "role_tag": "role",
      "content_tag": "content",
      "user_tag": "user",
      "assistant_tag": "assistant",
      "system_tag": "system"
    }
  }
}
```

最常见的错误是数据明明使用 `messages`，却没有声明 `formatting: "sharegpt"`。LLaMA-Factory 默认
按 Alpaca 格式读取时会寻找 `instruction`，从而出现找不到字段或没有有效样本的错误。

### 5. Chat template 决定模型真正看到什么

模型不会直接看到 `instruction`、`from` 或 `role` 这些 JSON 字段名。训练框架先把结构化数据
转换为标准消息，再使用目标模型 tokenizer 中的 chat template 加入角色标记和特殊 token。

同一段消息经过不同模型模板后，可能类似：

```text
Qwen 风格：
<|im_start|>system
你是一个客服助手。<|im_end|>
<|im_start|>user
订单一直没发货。<|im_end|>
<|im_start|>assistant
请先在订单详情查看预计发货时间……<|im_end|>

Llama 风格：
<|begin_of_text|><|start_header_id|>system<|end_header_id|>
你是一个客服助手。<|eot_id|>……
```

示意中的特殊 token 只用于理解，不应该在不清楚模板实现时手工写进原始数据。正确链路是：

```text
保持数据中的角色与内容结构清晰
  ↓
选择与基础模型匹配的 template
  ↓
由框架统一添加特殊 token
  ↓
训练和推理使用同一套模板
```

如果训练使用 Qwen 模板，推理却换成另一种角色格式，模型可能出现角色标记泄漏、无法停止生成或
回答风格异常。因此，训练数据格式可以转换，但最终模板必须与所用模型和推理配置一致。

### 6. 哪些 token 应该计算损失？

以下是一条对话序列：

```text
system：你是一个售后助手。
user：订单一直没发货。
assistant：请先查看订单详情中的预计发货时间……
```

通常希望模型学习的是 assistant 的回答，而不是让它模仿用户问题。框架会用 loss mask 决定哪些
token 参与损失：

```text
system token      → 通常 mask，不计算回答损失
user token        → 通常 mask，不计算回答损失
assistant token   → labels，计算损失
padding token     → mask
```

但具体默认值取决于训练框架、数据类型和配置，不能只看原始 JSON 猜测。Hugging Face TRL 当前
支持：

- 对 prompt-completion 数据使用 `completion_only_loss`，默认只在 completion 上计算损失；
- 对会话数据设置 `assistant_only_loss=True`，只在 assistant 消息上计算损失；
- 如果 chat template 不能生成 assistant mask，`assistant_only_loss` 可能无法正确工作。

详见 [TRL SFTTrainer 的损失配置](https://huggingface.co/docs/trl/en/sft_trainer)。在正式训练前应
抽取一条样本，打印模板化文本、`input_ids`、`labels` 和被设置为 `-100` 的位置，确认模型究竟
在学习哪些 token。

另一个容易误解的点是“多轮对话只训练最后一轮”。这不是由 ShareGPT 格式自动保证的。以
LLaMA-Factory 的 Alpaca `history` 为例，官方明确说明历史中的助手回答也会被学习。是否只训练
最后一轮、所有助手轮次或整个序列，必须检查所用框架版本和训练参数。

### 7. JSON、JSONL、格式转换与质检

JSON 文件通常把全部样本放在一个数组中：

```json
[
  {
    "instruction": "把文本分类为 positive 或 negative。",
    "input": "物流很快。",
    "output": "positive"
  },
  {
    "instruction": "把文本分类为 positive 或 negative。",
    "input": "商品已经损坏。",
    "output": "negative"
  }
]
```

JSONL 则每行一个完整对象，没有外层数组，行尾也没有逗号：

```jsonl
{"instruction":"把文本分类为 positive 或 negative。","input":"物流很快。","output":"positive"}
{"instruction":"把文本分类为 positive 或 negative。","input":"商品已经损坏。","output":"negative"}
```

两者的工程差异为：

| 对比 | JSON | JSONL |
| --- | --- | --- |
| 外层结构 | 通常是数组 | 每行一个对象 |
| 增量追加 | 需要重写数组或谨慎处理逗号 | 可以按行追加 |
| 流式读取 | 通常需要解析整体结构 | 易于逐行处理 |
| 单行故障定位 | 相对不直观 | 可以直接定位行号 |
| 人工查看嵌套对象 | 格式化后较清楚 | 长消息可能挤在一行 |

从 Alpaca 转换为 OpenAI 消息格式时，按下面顺序构造即可：

```text
system（如果存在）
  ↓
history 中每一组 user / assistant
  ↓
当前 user = instruction + 可选 input
  ↓
当前 assistant = output
```

反向转换只有在消息结构足够简单时才无损。如果数据包含工具调用、观察结果、多个 system 消息或
复杂角色，强行塞回 `instruction/input/output/history` 容易丢失语义，此时应保留 ShareGPT/OpenAI
结构。

训练前至少执行下面的质检：

```text
[ ] JSON 能完整解析，或 JSONL 每一行都能独立解析
[ ] 每条样本有稳定且唯一的 sample_id
[ ] Alpaca 的 instruction、output 非空
[ ] ShareGPT 的角色名称合法、顺序正确
[ ] 每条会话至少包含一个需要学习的 assistant / gpt 回答
[ ] system 规则与 output 内容没有冲突
[ ] 输出中没有混入参考答案提示、评测标签或内部元数据
[ ] 训练集、验证集和测试集没有重复或高度相似样本
[ ] 超长样本不会在截断后只剩问题、丢掉回答
[ ] 训练与推理使用同一类 chat template
```

格式正确只表示“框架能读取”，不表示训练数据正确。真正决定效果的仍是任务定义、回答质量、样本
覆盖、边界一致性和独立评测。

### 本节练习

先判断下面三个样本分别属于哪种格式或问题：

1. `{"instruction":"翻译成英文","input":"你好","output":"Hello"}`；
2. `{"messages":[{"role":"user","content":"你好"},{"role":"assistant","content":"你好！"}]}`；
3. `{"messages":[{"role":"user","content":"你好"},{"role":"user","content":"在吗？"}]}`。

参考答案：

| 题号 | 判断 |
| --- | --- |
| 1 | Alpaca 风格的单轮 SFT 样本 |
| 2 | OpenAI messages 风格，本质上属于会话消息格式 |
| 3 | 字段形式像 messages，但两个 user 连续出现且没有 assistant 目标，需要修复 |

再完成两个转换练习：

1. 把下面的 Alpaca 样本转换成 OpenAI `messages`；
2. 说明为什么包含 `function_call` 和 `observation` 的多轮数据不适合强行转换为简单 Alpaca。

```json
{
  "instruction": "提取问题类型。",
  "input": "订单两天没有发货。",
  "output": "not_shipped",
  "system": "只输出问题类型编码。"
}
```

转换结果：

```json
{
  "messages": [
    {
      "role": "system",
      "content": "只输出问题类型编码。"
    },
    {
      "role": "user",
      "content": "提取问题类型。\n订单两天没有发货。"
    },
    {
      "role": "assistant",
      "content": "not_shipped"
    }
  ]
}
```

工具调用数据包含比“用户—助手文本对”更丰富的角色和状态，简单 Alpaca 字段没有天然位置保存这些
语义，错误转换可能让模型把工具结果当成用户输入或普通回答。

### 本节小结

本节的核心关系是：

```text
Alpaca
  = instruction + input → output
  = 适合结构清楚的单轮任务

ShareGPT / OpenAI messages
  = 有序角色消息列表
  = 适合多轮、工具调用和复杂对话

JSON / JSONL
  = 文件封装方式
  ≠ 新的训练语义格式
```

两种格式最终都要经过字段映射、聊天模板、分词和 loss mask，才会成为真正的训练张量。选择格式时
不要只看哪个例子更短，而应看业务数据是否需要多轮角色、工具状态和无损扩展。对后续
LLaMA-Factory 实战，单轮分类与抽取可优先使用 Alpaca；客服多轮对话、Agent 和工具调用数据应
优先使用 ShareGPT/OpenAI messages，并在 `dataset_info.json` 中明确声明 `formatting`、`columns`
和 `tags`。

## 03 SFT 中的数据清洗与数据质量

### 本节目标

学完这一节，应该能够：

- 解释 SFT 数据清洗不只是“删空格、删空值”；
- 对 Alpaca、ShareGPT/OpenAI messages 数据进行结构校验；
- 识别重复、近似重复、标签冲突、隐私泄露和评测集污染；
- 从正确性、指令遵循、完整性、一致性和业务代表性判断数据质量；
- 用模型的真实 tokenizer 检查长度、截断和可训练 token；
- 正确划分训练集、验证集和测试集，避免同源样本跨集合泄漏；
- 建立可复现、可审计、可回滚的数据清洗流水线。

先记住本节最重要的一句话：

> SFT 学的不是“客观世界中唯一正确的回答”，而是训练数据里反复出现的回答规律；数据中的错误、
> 冲突、偏见和固定话术，也会被模型一起学习。

一套常见的数据处理链路是：

```text
原始数据
  ↓
结构与字段校验
  ↓
文本规范化、隐私与授权检查
  ↓
精确去重、近似去重、冲突处理
  ↓
质量审核与分布分析
  ↓
按来源分组划分 train / validation / test
  ↓
聊天模板渲染、分词与截断检查
  ↓
生成可追踪的训练数据版本
```

### 1. 数据清洗到底在清什么？

“数据能被 JSON 解析”只代表文件语法正确，不代表它是一份可训练的高质量数据。SFT 数据至少要
通过以下几层检查：

| 层次 | 主要问题 | 典型后果 |
|---|---|---|
| 文件层 | JSON 损坏、JSONL 某行无法解析、编码异常 | 训练程序直接报错 |
| 结构层 | 字段缺失、类型错误、角色不合法、空输出 | 样本无法映射，或没有可计算 loss 的 token |
| 内容层 | 答案错误、答非所问、前后矛盾、格式不一致 | 模型学习错误知识或不稳定行为 |
| 数据集层 | 重复、冲突、类别失衡、单一模板占比过高 | 过拟合、偏科，离线分数虚高 |
| 安全合规层 | 手机号、密钥、客户记录、未授权内容 | 隐私、安全和版权风险 |
| 评测层 | 训练集与测试集重复或同源 | 看起来效果很好，上线却失效 |
| 工程层 | 不记录来源和清洗版本 | 无法复现、审计和回滚 |

因此，高质量 SFT 数据通常具有这些特征：

- **正确**：事实、标签、计算结果和工具状态可靠；
- **相关**：回答真正解决了指令，而不是只包含相似关键词；
- **完整**：具备完成任务所需的信息，没有把关键条件截断；
- **一致**：同一规则在不同样本中得到兼容的答案；
- **有代表性**：覆盖真实用户、常见任务、长尾和失败边界；
- **适合学习**：输出风格清楚，不含无意义模板噪声；
- **合法安全**：数据获得授权，并妥善处理隐私和机密；
- **可追踪**：能知道样本来自哪里、经过哪些变换、为何被保留。

数据质量并不等于“句子写得漂亮”，而是**样本是否准确表达了希望模型学会的行为**。例如训练
情绪分类模型时，输出 `negative` 虽然很短，却可能比一段优美解释更符合任务目标。

### 2. 第一道关：结构与字段校验

结构校验应尽量自动化，并在训练前失败，而不是训练数小时后才发现字段映射错了。最低限度要检查：

- JSON 文件整体可解析；JSONL 文件每一行都能独立解析；
- 每条样本拥有稳定且唯一的 `sample_id`；
- Alpaca 数据的 `instruction` 和 `output` 非空，字段类型为字符串；
- ShareGPT/OpenAI messages 数据的角色合法、顺序合理，并至少存在一条助手输出；
- 工具调用与工具观察结果能够配对，不能把 observation 错当成用户消息；
- `dataset_info.json` 的字段映射与真实数据一致；
- 聊天模板渲染后，确实存在需要计算 loss 的助手 token；
- 分词与截断后，目标答案没有被全部截掉。

下面的数据语法正确，却不适合直接训练：

```json
[
  {
    "sample_id": "s-001",
    "instruction": "判断评论情绪，只输出 positive 或 negative。",
    "input": "物流太慢了。",
    "output": ""
  },
  {
    "sample_id": "s-001",
    "instruction": "判断评论情绪，只输出 positive 或 negative。",
    "input": 12345,
    "ouput": "negative"
  }
]
```

其中至少有四个问题：第一条输出为空；两个 `sample_id` 重复；第二条输入类型错误；`output`
被误写成了 `ouput`。如果程序把未知字段静默忽略，第二条也会变成“无答案样本”。

修复后可以是：

```json
[
  {
    "sample_id": "s-001",
    "instruction": "判断评论情绪，只输出 positive 或 negative。",
    "input": "物流太慢了。",
    "output": "negative"
  },
  {
    "sample_id": "s-002",
    "instruction": "判断评论情绪，只输出 positive 或 negative。",
    "input": "质感很好，值得购买。",
    "output": "positive"
  }
]
```

对于多轮数据，还要检查角色序列。例如 `user → assistant → user → assistant` 通常合理，而连续
出现两个 `assistant` 是否合理，要由当前框架的格式规范和业务语义共同判断。LLaMA-Factory 的
[数据格式说明](https://github.com/hiyouga/LlamaFactory/blob/main/data/README.md)还规定了哪些
角色属于输入、哪些角色的 token 参与学习；角色映射错误会直接改变训练目标。

如果使用推理模型或带思考模板的模型，还要保证训练和推理时的 thinking 配置一致。不要为了增加
字段而自动编造“思维链”；未经验证的推理过程可能比一个正确的简洁答案制造更多错误监督。

### 3. 第二道关：内容规范与隐私处理

文本规范化的目的，是消除**无意义差异**，同时保留**有意义结构**。常见操作包括：

- 统一 Unicode 表示、文件编码和换行符；
- 删除首尾多余空白、不可见控制字符和采集残留；
- 按业务需要清理 HTML 标签、网页导航和广告文本；
- 统一已定义的标签拼写，例如 `Negative`、`NEG` 全部映射为 `negative`；
- 修复确定无疑的乱码、截断和转义错误；
- 检查指令、输入和答案使用的语言是否符合数据集设计。

但不能机械地“全部转小写、删除所有标点、合并所有换行”。代码缩进、Markdown 层级、JSON 转义、
数学符号以及合同中的标点都可能影响语义。适合传统词袋模型的强力文本清洗，未必适合大语言模型。

隐私与合规检查至少应覆盖：

- 姓名、手机号、邮箱、身份证号、地址、订单号等个人信息；
- API key、访问令牌、密码、内部域名和数据库连接串；
- 客户工单、医疗记录、财务数据等敏感业务内容；
- 数据许可、用户授权、保留期限和删除要求；
- 模型输出中是否照抄了输入里的秘密信息。

例如：

```text
清洗前：客户王某的手机号是 13812345678，请查询订单。
清洗后：客户 <PERSON_001> 的手机号是 <PHONE_001>，请查询订单。
```

同一段对话中的同一个实体应使用一致占位符，否则会破坏指代关系。如果号码本身是任务必要信息，
也应考虑使用受控的合成值，而不是留下真实值。

隐私扫描可以用规则、词典和模型辅助，但不能把“工具没有检出”当成绝对安全。高敏感数据需要人工
抽检，并记录数据来源、授权依据和处理方式。

### 4. 第三道关：去重、冲突与数据泄漏

重复数据会使少数样本在 loss 中被反复计算，相当于人为提高它们的权重。去重通常分为两类：

- **精确重复**：规范化后的指令、输入和输出完全相同，可用哈希快速发现；
- **近似重复**：只改了标点、变量名、商品名或少量措辞，可用 n-gram、MinHash 或向量相似度
  发现候选，再结合规则或人工确认。

去重不能只看输入。两条输入相同、输出不同的数据可能代表：

1. **真正冲突**：同一句“物流太慢”一条标为 positive，一条标为 negative，应回到标注规则和
   原始来源裁决；
2. **多种正确回答**：开放式问答可能有多个同样优秀的表述，可以保留；
3. **条件丢失**：原始样本可能有地区、时间或系统指令差异，清洗时误删后才看起来冲突；
4. **任务定义变化**：旧版和新版规则不同，应记录 guideline version，不能直接混在一起。

处理顺序非常重要：

```text
推荐：先规范化和去重 → 再按来源分组 → 最后划分数据集

错误：先随机划分 → 再分别去重
      同一模板或同一客户对话可能同时进入训练集和测试集
```

划分时应使用 `customer_id`、`conversation_id`、`document_id`、模板族或来源批次进行
**group split**：同一组的样本只能进入一个集合。划分完成后，再做一次跨集合的精确和近似重复
检查。

测试集还需要被冻结。测试答案不能回流到训练数据中，也不能在反复调参时被当作开发集使用。否则
模型选择过程已经“看见”测试集，最终成绩就不再代表未知数据上的效果。

### 5. 怎样判断一条 SFT 数据质量？

可以给每条样本建立一张统一评分卡：

| 维度 | 审核问题 |
|---|---|
| 正确性 | 标签、事实、引用、计算和工具结果是否正确？ |
| 指令遵循 | 输出是否满足角色、格式、语言、长度和边界要求？ |
| 完整性 | 是否遗漏回答任务所需的关键步骤或条件？ |
| 一致性 | 回答内部是否矛盾？与数据集规则是否一致？ |
| 简洁与可读性 | 是否清楚直接，没有无关套话和重复内容？ |
| 安全性 | 是否泄露隐私、鼓励危险行为或违反业务政策？ |
| 代表性 | 是否对应真实使用场景，而不是只对训练模板有效？ |
| 可追踪性 | 是否能定位来源、标注规则、审核状态和版本？ |

例如，用户要求“只输出情绪标签”，下面两个答案都可能在事实层面正确：

```json
{
  "input": "物流太慢了。",
  "output": "这条评论表达了对物流速度的不满，因此属于负面情绪。"
}
```

```json
{
  "input": "物流太慢了。",
  "output": "negative"
}
```

但如果接口契约要求只输出标签，第二条才是高质量监督数据。评价数据时必须以**明确的任务规范**
为标准，不能只凭审核者的个人写作偏好。

[LIMA 论文](https://arxiv.org/abs/2305.11206)展示了一个重要现象：用 1,000 条精心选择的
提示—回答样本，也可以明显改善一个 65B 模型的对齐表现。它支持“质量有时比盲目堆数量更重要”，
但不能推出“任何任务用 1,000 条就够了”，也不能证明少量 SFT 数据可以可靠注入大量新知识。

使用模型生成合成数据时，应额外记录生成模型、版本、提示词和生成时间，并进行规则检查与人工抽检。
合成数据能够补充长尾，但也可能复制教师模型的幻觉、偏见和固定话术。让同一个模型既生成答案又
审核答案，只能提供初筛，不能代替独立评测。

### 6. 长度、分布与真实业务覆盖

字符数不等于 token 数。必须使用最终训练模型的 tokenizer，并在套用真实 chat template 后统计：

- 输入 token、助手输出 token和总 token 的 p50、p95、p99；
- 超过 `cutoff_len` 或 `max_length` 的样本比例；
- 截断后仍保留多少助手输出 token；
- 因 loss mask 配置导致“零可训练 token”的样本数；
- 不同任务、语言、来源和难度下的长度分布。

如果一条样本有 4,500 token，而训练上限是 4,096，不能只写一句“会自动截断”。还要确认从哪一端
截断、系统指令是否还在、答案是否被截掉。常见处理方式是合理切分文档、缩短无关上下文、过滤异常
长样本，或在显存与速度允许时提高上下文长度。

数量分布同样会改变模型行为。建议统计：

- 标签、任务类型、业务意图、语言和渠道占比；
- 正常案例、边界案例、拒答案例和失败恢复案例占比；
- 不同标注员、数据来源、模板和时间批次占比；
- 每个类别的准确率，而不只是整体平均分。

“类别平衡”不是永远把每类变成相同数量。如果线上 90% 是正常咨询、1% 是高风险请求，训练时可以
通过重采样提高稀有类别的学习权重，但验证集和测试集仍应包含贴近真实业务的分布，并单独报告高风险
类别指标。

如果 80% 样本来自同一种模板，模型可能学会识别模板，而不是理解任务。覆盖更多改写、真实表达、
噪声输入和长尾场景，比简单复制少数样本更有效。

### 7. 建立可复现的数据流水线

成熟的数据清洗不应依赖“某位同事在 Excel 里手工改过一遍”。推荐保留四层数据：

```text
raw/          原始快照，只读保存
cleaned/      经过确定性清洗的数据
splits/       train、validation、test 的样本 ID 清单
release/      某次训练实际使用的冻结版本
```

每条样本或旁路清单至少记录：

- `sample_id`、来源、采集时间和数据许可；
- 标注规范版本、标注者/生成器版本、审核状态；
- 执行过的 transform version；
- 保留、修复、删除或待复核，以及对应 reason code；
- 最终所属 split 和数据发布版本。

这些元数据用于审计，不应在没有业务意义时拼进模型输入。流水线每次运行应产出质量报告，至少包括：

| 指标 | 作用 |
|---|---|
| 解析和结构通过率 | 发现文件、字段、角色和类型错误 |
| 空指令、空输出率 | 发现无监督目标的样本 |
| 精确/近似重复率 | 判断数据有效规模和过采样风险 |
| 冲突率与待复核数 | 发现规则和标注一致性问题 |
| 隐私与密钥命中数 | 控制安全合规风险 |
| token p50/p95/p99、截断率 | 设置上下文长度并控制资源成本 |
| 各标签/任务/来源占比 | 检查覆盖和分布偏差 |
| 跨 split 重复率 | 发现数据泄漏 |
| 人工抽检通过率 | 验证自动规则没有漏掉语义问题 |

清洗规则也需要测试。例如，给每条规则准备“必须修改”和“绝不能修改”的样本，防止一次正则表达式
更新把代码缩进、负号或 JSON 转义一起破坏。

数据准备好后，不要立即以训练 loss 下降作为成功标准。先冻结基线评测，再训练，再比较同一套验证
和测试指标。OpenAI 的 [SFT 指南](https://developers.openai.com/api/docs/guides/supervised-fine-tuning)
也把“先建立可靠评测”放在投入微调之前；无论使用云端 API 还是本地框架，这个工程原则都成立。

### 本节练习

假设你收到 10,000 条客服 SFT 原始数据，请完成以下判断：

| 情况 | 建议动作 | 原因 |
|---|---|---|
| 同一问答完整重复 20 次 | 去重，必要时改用显式采样权重 | 避免无意放大该样本 |
| 同一投诉一条标为“退款”，一条标为“补发” | 待复核 | 可能是冲突，也可能遗漏了业务条件 |
| 输入中含客户真实手机号 | 脱敏或删除 | 控制隐私泄露风险 |
| 样本总长 9,000 token，训练上限 4,096 | 检查后切分、缩短或过滤 | 自动截断可能删掉答案 |
| 同一问题有两种都正确的自然表达 | 可以保留 | 开放生成允许多种优质答案 |

再为自己的数据集写一份“进入训练集的最低标准”，至少回答：

1. 哪些字段必须存在，允许哪些角色和标签？
2. 什么情况自动删除，什么情况必须人工复核？
3. 精确重复、近似重复和冲突分别如何处理？
4. 哪些字段属于敏感信息，如何脱敏？
5. 训练集、验证集、测试集按什么 group 划分？
6. 最大 token 长度是多少，怎样判断答案是否被截断？
7. 人工抽检多少条，按哪些维度评分？
8. 如何记录数据版本、规则版本和删除原因？

最后计算一次数据产出率：

```text
可用率 = 最终通过质量门槛的样本数 ÷ 原始样本数
```

可用率低不一定是坏事，它可能说明原始数据噪声很大、质量门槛有效。真正要关注的是：被删除的原因
是否可解释，保留下来的数据能否覆盖业务目标。

### 本节小结

本节的核心关系是：

```text
高质量 SFT 数据
  = 结构正确
  + 目标答案可靠
  + 重复和冲突受控
  + 隐私与授权合规
  + 长度和业务分布合理
  + train / validation / test 无泄漏
  + 全流程可追踪、可复现
```

清洗不是把文本改得越统一越好，而是去除无意义噪声、保留任务需要的语义。数据也不是越多越好：
一条错误且重复一百次的样本，比一条错误样本危害更大。进入训练前，应先用明确的数据规范、自动化
检查、人工抽检和冻结评测集建立质量门槛；训练后再用任务指标验证，而不是只看训练 loss。

## 04 模型训练 LoRA 方案解读

### 本节目标

学完这一节，应该能够：

- 解释 LoRA 为什么属于参数高效微调，而不是一种新的训练目标；
- 用低秩矩阵理解 LoRA 到底给模型增加了什么；
- 区分基础模型参数、LoRA 参数以及最终生效权重；
- 解释 LoRA 为什么节省训练显存，又为什么仍需加载基础模型；
- 区分 LoRA、QLoRA、冻结部分层和全量微调；
- 看懂一份 LLaMA-Factory LoRA SFT 配置的主要组成；
- 理解 adapter 的保存、加载、切换和合并；
- 判断一个项目是否适合优先尝试 LoRA。

术语上建议写成 **LoRA**，全称是 **Low-Rank Adaptation（低秩适配）**。“SFT”与“LoRA”不在
同一维度：

```text
SFT：模型根据什么训练目标学习？
LoRA：训练时以什么方式更新参数？

所以可以组合成：SFT + LoRA、DPO + LoRA
```

### 1. LoRA 解决了全量微调的什么问题？

全量微调会让基础模型中的所有可训练权重都参与反向传播和优化。模型越大，需要维护的内容越多：

- 基础模型权重；
- 每个可训练参数的梯度；
- Adam 等优化器的一阶、二阶状态；
- 前向传播中为了反向传播而保留的激活值；
- 多卡训练时的通信和中间缓冲区。

假设企业要针对 20 个业务分别训练全量模型，不仅训练成本高，还可能需要保存和部署 20 份完整权重。
LoRA 的思路是：

> 冻结基础模型的大矩阵，只学习一组规模很小的“权重改变量”。

训练结束后，每个业务只需保存自己的 LoRA adapter，并与同一个基础模型配套使用。它主要解决的是
**可训练参数、梯度、优化器状态和多任务权重存储**问题。

[LoRA 原始论文](https://arxiv.org/abs/2106.09685)在其研究对象上报告：相对于 GPT-3 175B 的
Adam 全量微调，LoRA 可把可训练参数减少约 10,000 倍、GPU 显存需求减少约 3 倍，同时在论文测试
的多种模型和任务上达到与全量微调相当或更好的效果。这是特定实验结果，不是所有模型、数据和硬件
都能复现的固定比例。

LoRA 也不是“把大模型训练成一个小模型”。推理时仍然需要基础模型；adapter 只是改变基础模型的
部分计算结果。

### 2. LoRA 的核心：把大矩阵更新写成两个小矩阵

神经网络中的一个线性层原本可以写成：

$$
y = W_0x
$$

其中 `W_0` 是预训练得到的权重。全量微调直接修改 `W_0`；LoRA 冻结 `W_0`，把训练得到的变化
表示为两个低秩矩阵的乘积：

$$
\Delta W = BA
$$

$$
y = W_0x + \frac{\alpha}{r}BAx
$$

若原矩阵形状为：

$$
W_0 \in \mathbb{R}^{d_{out} \times d_{in}}
$$

则两个小矩阵可以是：

$$
A \in \mathbb{R}^{r \times d_{in}}, \qquad
B \in \mathbb{R}^{d_{out} \times r}
$$

这里的 rank `r` 远小于 `d_{in}` 和 `d_{out}`。训练时只更新 `A` 和 `B`：

```text
全量更新参数量：d_out × d_in
LoRA 更新参数量：r × d_in + d_out × r
```

例如一个 `4096 × 4096` 的线性层包含 `16,777,216` 个权重。若 `r = 8`，LoRA 的两个矩阵
只有：

```text
8 × 4096 + 4096 × 8 = 65,536 个参数
65,536 ÷ 16,777,216 ≈ 0.39%
```

这是**单个线性层**的示意，不等于整个模型最终也是 0.39%；最终比例还取决于目标模块、层数以及
是否额外训练 embedding、输出层或 bias。

为什么可以这样做？LoRA 假设：模型适应某个下游任务时，真正需要的权重变化可能集中在一个维度较低
的子空间里，不一定要自由修改原矩阵的每个方向。低秩是一种有效约束，但不是数学上保证所有任务都
能无损表示。

### 3. LoRA 被加在 Transformer 的什么位置？

Transformer 中有大量线性投影，例如注意力模块常见的：

```text
q_proj：生成 Query
k_proj：生成 Key
v_proj：生成 Value
o_proj：注意力输出投影
```

MLP/FFN 中也有 `gate_proj`、`up_proj`、`down_proj` 等线性层。LoRA 可以只加到部分注意力
投影，也可以覆盖更多甚至全部线性层：

```text
输入 x
  ├─ 冻结路径：W₀x
  └─ LoRA 路径：A 降到 r 维 → B 映射回输出维度 → 按比例缩放
                  ↓
             两条路径相加
```

目标模块选择直接影响：

- 可训练参数量和显存；
- 模型能够调整的范围；
- 训练速度和最终效果；
- adapter 与基础模型架构的兼容性。

不同模型的模块名不一定相同，不能把另一种架构的 `q_proj` 配置直接照搬过来。应先查看模型结构，
再使用当前框架支持的模块名。Hugging Face PEFT 的
[LoRA 文档](https://huggingface.co/docs/peft/main/package_reference/lora)指出，LoRA 原则上可用于
任意一组权重矩阵；最终参数量主要由矩阵形状、rank 和选中的目标模块共同决定。

adapter 还与基础模型的架构、权重版本、目标模块和 tokenizer/chat template 绑定。即使两个模型都
叫“7B”，也不能假设 adapter 可以互换。

### 4. 一次 LoRA 训练到底更新了什么？

以 SFT + LoRA 为例，单个 batch 的过程可以理解为：

```text
1. 训练数据经过 chat template 和 tokenizer
2. 基础模型 W₀ 与 LoRA 分支 A、B 一起完成前向传播
3. 根据目标 token 计算 SFT loss
4. 梯度穿过整个计算图
5. W₀ 保持冻结，不保存它的梯度和优化器状态
6. 优化器只更新 LoRA 参数 A、B，以及显式指定的其他可训练模块
```

“基础模型冻结”不等于“基础模型不参与计算”。为了算出预测结果和 LoRA 参数的梯度，每一层仍然要
执行前向传播，反向传播也需要经过相关计算路径。差异是基础权重本身不被优化器改写。

标准初始化通常让训练开始时的 LoRA 分支近似零改动，因此初始模型行为接近原基础模型，随后再逐步
学习新行为。具体初始化方式取决于框架和配置，不能假设所有 LoRA 变体都完全相同。

训练完成后，逻辑上的有效权重是：

$$
W_{\text{effective}} = W_0 + \Delta W
$$

但磁盘上不一定立即产生一份完整模型。常见输出是：

```text
adapter_model.*       学到的 LoRA 参数
adapter_config.json   rank、alpha、目标模块、基础模型等配置
trainer_state.json    训练状态；是否保存取决于框架配置
```

加载时必须同时具备匹配的基础模型和 adapter。只复制 adapter 文件，通常不能独立推理。

### 5. LoRA 为什么省显存，但不是“显存只剩 1%”？

训练显存可以粗略拆成：

```text
训练显存
  ≈ 基础模型权重
  + 可训练参数
  + 梯度
  + 优化器状态
  + 激活值
  + 临时缓冲和框架开销
```

LoRA 大幅减少的是**可训练参数对应的梯度和优化器状态**，并缩小需要保存的微调权重。它不会自动
消除：

- 基础模型权重所占显存；
- 与 batch size、序列长度、层数相关的激活显存；
- 注意力计算和前向传播成本；
- CUDA kernel、缓存、碎片和分布式通信开销。

所以“只训练 0.5% 参数”不能直接推出“只用全量微调 0.5% 的显存”。在长上下文训练中，激活值
甚至可能成为主要瓶颈，还需要 gradient checkpointing、Flash Attention、减小 batch size 或缩短
序列等技术。

LoRA 通常也不会让每一步训练速度按可训练参数比例提升。基础模型的前向和反向计算仍在，只是参数
更新与通信的负担降低。实际峰值显存和吞吐量应以目标模型、精度、序列长度、batch、硬件和框架实测
为准。

### 6. LoRA、QLoRA、冻结部分层和全量微调怎么选？

| 方案 | 基础权重 | 主要更新对象 | 优势 | 主要代价或限制 |
|---|---|---|---|---|
| LoRA | 通常以 BF16/FP16 等精度加载并冻结 | 低秩 adapter | 成本低、adapter 小、便于多任务管理 | 仍要在显存中加载完整基础模型 |
| QLoRA | 低比特量化后冻结 | 较高精度的 LoRA adapter | 进一步压缩基础权重显存 | 量化兼容性、速度和效果需要实测 |
| 冻结部分层 | 一部分冻结，一部分原层参与训练 | 选中的原模型参数 | 比 LoRA 更直接地修改部分层 | 可训练参数和 checkpoint 往往更大 |
| 全量微调 | 不冻结 | 全部参数 | 调整自由度最高 | 显存、训练、存储和多卡通信成本最高 |

QLoRA 不是“把 LoRA 参数也全部变成 4 bit”。其核心是用低比特形式加载并冻结基础模型，让梯度通过
量化基础模型回传到 LoRA adapter。原始
[QLoRA 论文](https://arxiv.org/abs/2305.14314)使用 4-bit NormalFloat、double quantization 和
paged optimizers 等技术，在论文实验中显著降低了微调显存。

可以采用以下决策顺序：

1. **一般企业 SFT 原型**：先用 LoRA 建立数据—训练—评测闭环；
2. **LoRA 仍装不进显存**：在硬件与模型支持时评估 QLoRA；
3. **LoRA 指标明显达不到要求**：先排查数据、模板、loss mask 和超参数，再对比扩大目标模块、
   提高 rank、冻结部分层或全量微调；
4. **需要深度改变模型能力且数据、算力充分**：把全量微调作为实验对照，而不是仅凭直觉选择；
5. **只需补充实时知识**：优先评估 RAG，不要把知识库更新问题误当成 LoRA 问题。

LoRA 并不保证效果一定等于全量微调。任务差异越大、需要改变的能力越复杂，低秩约束越可能成为瓶颈；
但很多业务任务的数据规模和目标并不足以支撑稳定的全量微调，此时 LoRA 往往是更合理的起点。

### 7. 从训练配置到部署的完整流程

LLaMA-Factory 当前的 LoRA SFT 配置可以简化理解为：

```yaml
model_name_or_path: Qwen/Qwen3-4B-Instruct-2507

stage: sft
do_train: true
finetuning_type: lora
lora_rank: 8
lora_target: all

dataset: your_sft_dataset
template: qwen3_nothink
cutoff_len: 2048

output_dir: saves/qwen3-4b/lora/sft
per_device_train_batch_size: 1
gradient_accumulation_steps: 8
learning_rate: 1.0e-4
num_train_epochs: 3
bf16: true
```

这段配置只是结构示例，不能原样用于所有模型。模型与 `template` 必须匹配；`bf16` 要求硬件支持；
数据集要先在 LLaMA-Factory 中注册；学习率、rank、目标模块、长度和 batch 均需用验证集选择。官方
[SFT 文档](https://llamafactory.readthedocs.io/en/latest/getting_started/sft.html)也把模型、
微调方式、数据、模板、输出、batch、学习率和训练轮数列为关键配置。

一套可靠流程是：

```text
1. 冻结基线评测集，记录基础模型成绩
2. 清洗并版本化训练数据
3. 确认 model、tokenizer、chat template 完全对应
4. 注入 LoRA，并打印 trainable params 验证目标模块
5. 先用极小数据跑通，检查 loss、样本渲染和 checkpoint
6. 正式训练，同时观察训练/验证 loss 和任务指标
7. 用冻结测试集对比 base 与 base + adapter
8. 保存 adapter、配置、数据版本、代码版本和评测报告
9. 选择动态加载 adapter 或合并权重，再做一次部署回归测试
```

部署有两种常见方式：

- **不合并**：保留一份基础模型，按业务加载或切换多个 adapter，版本管理灵活；
- **合并**：计算 `W_0 + \Delta W` 并生成完整权重，部署链路更简单，也可消除普通 LoRA 分支的
  额外计算，但会失去轻量切换优势。

合并前后都要回归测试。尤其当基础模型以低比特形式加载时，合并、反量化和重新量化的顺序可能影响
结果。还应保留原始基础模型和 adapter，避免只留下一个无法追溯的合并产物。

### 本节练习

**练习 1：计算参数量**

某线性层的输入、输出维度都是 4096，LoRA rank 为 16：

```text
全量矩阵参数量 = 4096 × 4096 = 16,777,216
LoRA 参数量     = 16 × 4096 + 4096 × 16 = 131,072
比例            = 131,072 ÷ 16,777,216 ≈ 0.78%
```

如果把 rank 从 16 增加到 32，LoRA 参数量将近似翻倍，但这不保证验证集指标也按比例提高。

**练习 2：判断说法**

| 说法 | 判断 | 原因 |
|---|---|---|
| LoRA 训练不需要加载基础模型 | 错 | 前向传播仍依赖基础模型 |
| SFT 和 LoRA 是二选一 | 错 | 一个是训练目标，一个是参数更新方式 |
| adapter 可以任意换到另一个 7B 模型 | 错 | 它依赖具体基础权重和模块结构 |
| 只训练 1% 参数就只需 1% 显存 | 错 | 基础权重、激活和缓冲仍占显存 |
| QLoRA 的基础权重通常保持冻结 | 对 | 低比特基础模型负责计算，主要更新 adapter |
| 训练 loss 下降就证明 LoRA 有用 | 错 | 还要与基础模型做冻结评测集对比 |

**练习 3：为业务选择方案**

一家企业要让模型稳定地把售后消息分成 20 个意图，已有 8,000 条审核数据，单卡无法进行全量微调。
合理起点是：

1. 先评测提示词能否达标；
2. 若不达标，尝试 SFT + LoRA；
3. 如果基础模型权重仍装不下，再评估 QLoRA；
4. 用每个意图的 precision、recall、F1 和混淆矩阵对比基础模型；
5. 只有在数据、配置和 LoRA 容量排查后仍不够时，才扩大训练方案。

### 本节小结

本节的核心关系是：

```text
基础模型：W₀，冻结但仍参与计算
LoRA 更新：ΔW = BA，只训练小矩阵 A、B
最终效果：W₀x + ΔWx

LoRA
  ≠ 新的训练目标
  ≠ 不需要基础模型
  ≠ 显存按可训练参数比例下降
  = 一种参数高效的模型适配方式
```

LoRA 的价值，是用低秩更新约束换取更低的训练、存储和多任务管理成本。它通常是企业尝试 SFT 或
DPO 时很实用的第一选择，但最终是否合适仍要由冻结评测集决定。下一节将专门分析 LoRA 的四个核心
调节参数：rank、alpha、dropout 和 target modules，以及它们之间的联动关系。

## 05 LoRA 的 4 个核心调节参数解析

### 本节目标

学完这一节，应该能够：

- 解释 rank、alpha、dropout 和 target modules 各自控制什么；
- 计算修改 rank 或 target modules 后的可训练参数变化；
- 区分 LoRA 容量、作用强度、正则化和作用范围；
- 解释为什么 alpha 与学习率相关，却不能相互替代；
- 识别普通 LoRA 与 rsLoRA 的缩放公式差异；
- 根据欠拟合、过拟合、不稳定和显存不足选择调参方向；
- 用控制变量实验寻找参数，而不是照抄“万能配置”。

四个参数可以先记成一句话：

```text
rank           决定每个 LoRA 分支有多大容量
alpha          决定 LoRA 更新以多大比例影响原模型
dropout        决定训练时对 LoRA 分支施加多少随机正则化
target modules 决定 LoRA 被安装到模型的哪些位置
```

不同框架的字段名略有区别：

| 含义 | LLaMA-Factory 常用字段 | Hugging Face PEFT 字段 |
|---|---|---|
| 秩 | `lora_rank` | `r` |
| 缩放系数 | `lora_alpha` | `lora_alpha` |
| Dropout 概率 | `lora_dropout` | `lora_dropout` |
| 目标模块 | `lora_target` | `target_modules` |

这些参数有默认值，但默认值只表示框架能够启动，不代表对当前业务最优。

### 1. rank：LoRA 更新矩阵的容量

对于一个形状为 `d_out × d_in` 的原始线性层，LoRA 使用：

$$
A \in \mathbb{R}^{r \times d_{in}}, \qquad
B \in \mathbb{R}^{d_{out} \times r}
$$

因此该层新增的参数量是：

$$
N_{\text{LoRA}} = r(d_{in} + d_{out})
$$

rank `r` 越大：

- LoRA 可表达的权重变化更丰富；
- 可训练参数、梯度、优化器状态和 adapter 文件通常线性增加；
- 对训练数据的拟合能力增强；
- 训练时间和显存可能上升；
- 小数据上的过拟合风险可能增加。

rank 越小则成本更低、约束更强，但如果任务需要的变化无法被低秩空间表达，训练集和验证集都可能
欠拟合。

以 `4096 × 4096` 线性层为例：

| rank | LoRA 参数量 | 占原矩阵参数量 |
|---:|---:|---:|
| 4 | 32,768 | 约 0.20% |
| 8 | 65,536 | 约 0.39% |
| 16 | 131,072 | 约 0.78% |
| 32 | 262,144 | 约 1.56% |
| 64 | 524,288 | 约 3.13% |

表中只计算一个线性层。整个模型的 LoRA 参数量还要乘以命中的模块数，并对不同形状的层分别求和：

$$
N_{\text{total}} = \sum_{i \in \text{targets}} r_i(d_{in,i}+d_{out,i})
$$

实战中可把 8 或 16 作为低成本实验起点，再根据验证集比较 32、64 等配置，但这些只是常见搜索点，
不是行业标准。模型参数更多，也不意味着 rank 必须同比例增大。

判断 rank 是否太小，不能只看训练 loss 某一时刻的数值。应先排除错误模板、错误 loss mask、数据
质量和学习率问题；如果训练集、验证集指标都停在较差水平，并且扩大 rank 能稳定改善验证结果，才有
证据说明原容量不足。

### 2. alpha：控制 LoRA 分支的作用强度

普通 LoRA 常见的前向公式是：

$$
y = W_0x + \frac{\alpha}{r}BAx
$$

其中 `alpha` 本身不会增加参数量，它通过缩放因子：

$$
s = \frac{\alpha}{r}
$$

改变 LoRA 分支对最终输出的影响。比如：

| rank | alpha | 普通 LoRA 缩放 `alpha / r` |
|---:|---:|---:|
| 8 | 8 | 1 |
| 8 | 16 | 2 |
| 16 | 16 | 1 |
| 16 | 32 | 2 |

做 rank 对照实验时，把 `alpha / r` 保持不变是一种常见的控制变量方法。例如从 `r=8,
alpha=16` 改成 `r=16, alpha=32`，容量发生变化，而名义缩放仍为 2。不过“比例相同”不保证
训练动态完全相同，因为矩阵维度、初始化、梯度噪声和优化过程也变了。

alpha 太小，LoRA 更新可能很难显著改变基础模型；alpha 太大，则可能导致更新过强、训练不稳定，
或者更快破坏原模型的通用能力。但出现这些现象时也必须同时检查学习率、梯度范数和数据。

**alpha 与学习率不是同一个旋钮：**

- 学习率控制优化器每一步怎样改动 `A`、`B`；
- alpha 控制 `BAx` 在前向结果中以多大比例生效，也会影响对应梯度尺度；
- 两者都会影响训练强度，但不能简单认为“alpha 翻倍等于学习率翻倍”。

还要确认使用的是哪种 LoRA 变体。Hugging Face PEFT 的
[LoRA 参数文档](https://huggingface.co/docs/peft/package_reference/lora)说明：

```text
普通 LoRA：scaling = alpha / r
rsLoRA：    scaling = alpha / sqrt(r)
```

所以比较两次训练时，仅记录 rank 和 alpha 还不够，也要记录 `use_rslora` 等变体开关和框架版本。

### 3. dropout：LoRA 分支的训练正则化

`lora_dropout` 会在训练时随机屏蔽 LoRA 路径的一部分输入或激活，降低 adapter 对训练样本中偶然
模式的依赖。推理时 dropout 关闭，因此它：

- 不会减少 adapter 参数量；
- 不会让推理时随机丢信息；
- 主要影响训练过程和泛化能力；
- 不能修复错误标签、数据泄漏或测试集污染。

常见的实验值包括 `0`、`0.05`、`0.1`：

| 数据和现象 | 可尝试方向 |
|---|---|
| 数据较多、质量高，训练与验证差距小 | 从 0 或较小 dropout 开始 |
| 训练集持续变好，验证集开始恶化 | 适度提高 dropout，并检查轮数和重复数据 |
| 训练集本身也学不好 | 不要先加大 dropout，应先排查欠拟合原因 |
| 数据量很小且模板单一 | 适度 dropout 可能有帮助，但更应补充真实数据多样性 |

dropout 不是越大越安全。设得过高会使 LoRA 分支难以学习，表现为训练收敛慢、训练集指标也偏低。
对于确定性强的分类任务和大型高质量数据集，`0` 可能已经足够；对于小型、多噪声数据，`0.05` 或
`0.1` 值得作为对照。是否有效仍由验证集决定。

还要区分训练随机性：dropout、数据打乱和初始化都会让单次结果波动。如果两个配置只差很小，应该
固定随机种子，并在成本允许时重复运行，而不是把偶然波动解释为参数优劣。

### 4. target modules：LoRA 到底改模型的哪里

`target modules` 指定哪些原始模块获得 LoRA 分支。它既控制作用范围，也会显著改变总参数量。
在常见稠密 Transformer 中可能看到：

| 模块 | 作用 |
|---|---|
| `q_proj` | 生成注意力 Query |
| `k_proj` | 生成注意力 Key |
| `v_proj` | 生成注意力 Value |
| `o_proj` | 生成注意力输出 |
| `gate_proj` | 控制 MLP 门控 |
| `up_proj` | 映射到 MLP 中间维度 |
| `down_proj` | 映射回隐藏维度 |

几种常见范围是：

```text
只选 q_proj、v_proj
  → 成本较低，适合建立基线

选择 q_proj、k_proj、v_proj、o_proj
  → 允许调整完整注意力投影

选择注意力和 MLP 的线性层
  → 容量更大、参数更多，常称 all-linear 风格
```

“目标更多”不保证一定更好。它提高了适配自由度，也会增加显存、时间和过拟合空间。对知识、风格、
分类和复杂推理任务，最佳范围可能不同，需要实验验证。

模块名与模型架构相关。Llama/Qwen/Mistral 风格模型常能看到上述名称，但其他模型、MoE 模型或
融合实现可能不同。配置前应打印 `named_modules()` 或使用框架的模型结构信息，训练启动后再打印
可训练参数，确认配置确实命中预期模块。

还要注意框架语义：

- PEFT 的 `target_modules="all-linear"` 通常选择线性/Conv1D 模块，并按框架规则排除输出层；
- LLaMA-Factory 配置中的 `lora_target: all` 是其封装语义；
- 不应假设不同框架的 `all`、`all-linear` 或自动选择结果完全相同；
- 如果新增了 tokenizer token 或任务分类头，可能还要用 `modules_to_save` 训练并保存额外模块，
  这已经超出单纯的 LoRA 四参数。

### 5. 四个参数如何相互影响？

四个参数不是四条互不相关的滑杆：

```text
总容量与成本
  ≈ rank × 被 target modules 命中的矩阵规模

普通 LoRA 名义作用强度
  = alpha / rank

训练期正则化
  由 dropout 参与控制
```

例如把 rank 从 8 提高到 16，同时把目标模块从 `q_proj,v_proj` 扩展为全部注意力和 MLP 线性层，
改变的不只是 rank：参数量可能增加数倍，模型调整范围也完全不同。即使最终指标提高，也无法知道是哪
个变化起作用。

下面三组配置代表不同实验目的，而不是推荐答案：

```yaml
# A：低成本基线
lora_rank: 8
lora_alpha: 16
lora_dropout: 0.05
lora_target: q_proj,v_proj

---
# B：只测试 rank，保持普通 LoRA 的 alpha/r = 2
lora_rank: 16
lora_alpha: 32
lora_dropout: 0.05
lora_target: q_proj,v_proj

---
# C：只测试作用范围
lora_rank: 8
lora_alpha: 16
lora_dropout: 0.05
lora_target: all
```

对比 A 与 B，主要观察 rank 容量变化；对比 A 与 C，主要观察 target 范围变化。实际配置值还要确认
当前 LLaMA-Factory 版本和目标模型是否支持。

一个很有用的习惯是训练启动后记录：

```text
trainable params
all params
trainable percentage
实际命中的模块名称
LoRA scaling 公式
框架与依赖版本
```

否则配置写着 `target: all`，却可能因为命名或兼容问题没有命中预期层。

### 6. 用训练现象判断该调哪个参数

| 现象 | 优先排查 | 可能的参数方向 |
|---|---|---|
| 训练集和验证集都很差 | 数据、模板、loss mask、学习率、训练是否真正更新 | 再尝试扩大 target 或 rank |
| 训练集很好，验证集变差 | 重复数据、泄漏、训练轮数、分布差异 | 提高 dropout，或降低 rank/target 范围 |
| loss 剧烈震荡或出现 NaN | 学习率、精度、异常 batch、梯度范数 | 降低学习率或 alpha；检查梯度裁剪 |
| 训练后与基础模型几乎一样 | adapter 是否加载、目标模块是否命中、可训练参数是否为零 | 确认无误后再提高 alpha/rank |
| 显存不足 | 序列长度、batch、激活、量化和 checkpointing | 减少 target 或 rank 只能解决部分压力 |
| 未合并效果好，合并后变差 | 基础模型版本、dtype、量化与合并流程 | 通常不是靠调四参数解决 |

不要看到“效果不明显”就直接把四个参数全部调大。更可靠的搜索顺序是：

1. **先证明流水线正确**：用少量数据过拟合一个小 batch，确认 loss 能明显下降；
2. **固定数据和评测**：同一划分、同一训练步数、同一 seed、同一学习率作为基线；
3. **先比较 target 范围**：低成本注意力模块与更广范围做对照；
4. **再搜索 rank**：例如 8、16、32，并用验证集判断收益是否饱和；
5. **控制 scaling**：普通 LoRA 可先保持 `alpha/r` 一致，再单独微调 alpha；
6. **最后调 dropout**：依据训练—验证差距比较 0、0.05、0.1；
7. **联合优化学习率和轮数**：四参数不能脱离优化器与训练时长单独决定。

每次实验都应同时记录任务指标、峰值显存、训练时间和 adapter 大小。企业最终需要的是质量—成本最优
点，而不是验证集最高但资源翻倍、收益只有极小变化的配置。

### 7. 一套可直接使用的调参记录表

建议给每次实验分配唯一 ID，并至少记录：

| 字段 | 示例 |
|---|---|
| 实验 ID | `lora-r16-a32-d005-qv-seed42` |
| 基础模型与 revision | 精确到仓库 revision 或文件哈希 |
| 数据版本与 split | `sft-clean-v3` |
| rank / alpha / scaling | `16 / 32 / 2` |
| LoRA 变体 | 普通 LoRA，`use_rslora=false` |
| dropout | `0.05` |
| target modules | `q_proj,v_proj` |
| 可训练参数量 | 由训练日志实际打印 |
| 学习率、batch、步数、seed | 完整记录 |
| 验证与测试指标 | 总体指标与分组指标 |
| 峰值显存、时长、adapter 大小 | 用于成本比较 |

推荐采用逐层实验：

```text
阶段 0：确认数据、模板、loss mask、adapter 加载与评测正确
阶段 1：固定 rank/alpha/dropout，比较 target modules
阶段 2：固定 target/dropout/scaling，比较 rank
阶段 3：固定 rank/target，比较 alpha 或 scaling
阶段 4：根据过拟合差距比较 dropout
阶段 5：对候选配置重复 seed，并做最终冻结测试
```

Hugging Face PEFT 的[官方 LoRA 文档](https://huggingface.co/docs/peft/package_reference/lora)明确
定义了 `r`、`lora_alpha`、`lora_dropout` 和 `target_modules` 的语义；LLaMA-Factory 的
[SFT 配置文档](https://llamafactory.readthedocs.io/en/latest/getting_started/sft.html)则展示了
`lora_rank`、`lora_target` 等实际配置方式。使用时应以锁定版本的文档和训练日志为准。

### 本节练习

**练习 1：计算参数量**

某模型有 32 层，每层只对形状均为 `4096 × 4096` 的 `q_proj` 和 `v_proj` 加 LoRA。
当 `rank=8` 时：

```text
每个目标矩阵：8 × (4096 + 4096) = 65,536
目标矩阵总数：32 × 2 = 64
LoRA 参数总数：65,536 × 64 = 4,194,304
```

将 rank 改成 16 后，参数总数变为 `8,388,608`。改变 alpha 或 dropout 不会改变这个参数量。

**练习 2：设计控制变量**

基线是：

```yaml
lora_rank: 8
lora_alpha: 16
lora_dropout: 0.05
lora_target: q_proj,v_proj
```

请分别写出：

1. 只测试更高 rank，同时保持普通 LoRA scaling 不变的配置；
2. 只测试更大 target 范围的配置；
3. 只测试更强 dropout 的配置。

参考答案分别是 `rank=16, alpha=32`；仅修改 `lora_target`；仅把 dropout 改为如 `0.1`。一次
不要同时改多个变量。

**练习 3：诊断实验**

如果训练集准确率从 70% 提升到 99%，验证集却从 72% 下降到 68%，这更像过拟合。应先检查数据
重复与分布，再尝试减少轮数、降低容量或适度增加 dropout，而不是继续增大 rank 和 target 范围。

### 本节小结

本节的核心关系是：

```text
rank
  → 单个 LoRA 分支的容量和参数量

alpha
  → LoRA 分支的缩放强度
  → 普通 LoRA 为 alpha/r，rsLoRA 为 alpha/sqrt(r)

dropout
  → 训练期正则化，不改变参数量

target modules
  → LoRA 的作用位置、总容量与总体成本
```

调参时，先保证数据和训练链路正确，再用控制变量比较 target 范围、rank、alpha 和 dropout。不要把
某篇教程中的 `r=8, alpha=16, dropout=0.05` 当成固定答案；真正的答案是当前模型、数据、任务、
硬件和冻结评测集共同决定的质量—成本平衡点。

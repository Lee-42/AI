```text
用户问题和文档片段都要先变成向量，

```

这一章开始拆开向量数据库背后的底层逻辑。

课程结构大致是：

- 01 到底什么是向量？

- 07 向量维度是越多越好吗？

- 11 大量短句如何向量化？

先不要急着背算法名。

这一章最重要的是建立一条主线：

```text
文字 / 图片 / 音频
  ↓
模型编码
  ↓
向量
  ↓
相似度计算
  ↓
召回相关内容
  ↓
给大模型生成答案
```

## 01 到底什么是向量？

向量可以先用一句话理解：

```text
向量就是一组有顺序的数字。
```

例如：

```text
[0.21, -0.35, 0.88, 0.14]
```

这就是一个 4 维向量。

它有 4 个数字，每个数字占一个位置。

在 AI 场景里，向量通常不是 4 维，而是几百维、几千维，甚至更高。

例如一段文本可能被 embedding 模型转成：

```text
请婚假需要什么材料？
  ↓
[0.012, -0.348, 0.772, ..., -0.091]
```

这组数字本身人类看不懂，但机器可以拿它做计算。

### 1. 为什么 AI 需要向量？

计算机不能直接理解中文语义。

对计算机来说：

```text
婚假
年假
退款
发票
```

最开始都只是字符。

如果想让机器判断：

```text
“请婚假需要什么材料？”
```

和：

```text
“婚假申请需要提交结婚证复印件。”
```

这两句话是不是相关，就必须把它们变成可计算的形式。

向量解决的就是这个问题：

```text
把人类语言变成机器可以比较、排序、检索的数字。
```

这也是为什么 RAG 里会用向量。

因为 RAG 要解决的问题不是“关键词是否完全一样”，而是：

```text
用户问题和哪段资料在语义上最接近？
```

### 2. 向量可以理解成语义坐标

学习阶段，可以先用二维坐标来建立直觉。

例如在一个简化空间里：

```text
猫     -> [0.9, 0.8]
狗     -> [0.88, 0.76]
汽车   -> [-0.7, 0.2]
公交车 -> [-0.68, 0.25]
```

猫和狗的位置近，因为它们语义接近。

汽车和公交车的位置近，因为它们都和交通工具相关。

猫和汽车距离远，因为语义差异大。

真实 embedding 向量不是二维，而是高维。

但核心直觉一样：

```text
语义接近的内容，在向量空间里的距离通常更近。
语义差异大的内容，在向量空间里的距离通常更远。
```

所以向量也可以理解成：

```text
语义在数学空间里的坐标。
```

### 3. 向量不是简单编号

一种错误理解是：

```text
猫 = 1
狗 = 2
汽车 = 3
```

这只是编号，不是向量语义。

编号只能说明：

```text
它是谁。
```

但不能说明：

```text
它和谁更像。
它和谁经常一起出现。
它适合出现在什么上下文里。
它在语义空间里靠近什么概念。
```

如果只用编号，模型并不知道猫和狗更接近，也不知道汽车和公交车更接近。

向量的价值在于：

```text
它不仅表示身份，还能表示关系。
```

### 4. 向量里的每一维是什么意思？

初学时容易问：

```text
向量第 1 维代表什么？
第 2 维代表什么？
第 100 维代表什么？
```

在真实 embedding 模型里，通常不能简单解释成：

```text
第 1 维 = 动物
第 2 维 = 食物
第 3 维 = 科技
```

真实向量的维度是模型训练出来的隐含特征。

它们通常不是人手工命名的字段，而是模型为了完成训练任务自动形成的数字表示。

为了理解，可以用一个简化例子：

| 词语 | 动物特征 | 食物特征 | 公司特征 | 交通工具特征 |
| --- | ---: | ---: | ---: | ---: |
| 猫 | 0.95 | 0.02 | 0.00 | 0.00 |
| 狗 | 0.93 | 0.01 | 0.00 | 0.00 |
| 苹果 | 0.00 | 0.82 | 0.70 | 0.00 |
| 汽车 | 0.00 | 0.00 | 0.05 | 0.94 |

这个表只是帮助建立直觉。

真实模型不会这么直白。

但它说明了一件事：

```text
一个词、一句话、一段文档，可以同时拥有很多语义特征。
```

### 5. 文本向量是怎么来的？

在 RAG 里，我们通常不会自己手写向量。

而是调用 embedding 模型：

```text
文本
  ↓
embedding 模型
  ↓
向量
```

例如：

```text
“公司婚假需要提交什么材料？”
  ↓
embedding 模型
  ↓
[0.031, -0.128, 0.556, ..., 0.204]
```

文档片段也会做同样的事情：

```text
“婚假为 10 天，申请时需要提交结婚证复印件。”
  ↓
embedding 模型
  ↓
[0.028, -0.119, 0.581, ..., 0.198]
```

然后系统比较这两个向量的相似度。

如果相似度高，就说明：

```text
用户问题和这段文档可能相关。
```

注意这里说的是“可能相关”，不是“一定正确”。

最终还需要大模型基于检索片段生成答案。

### 6. 向量和 RAG 的关系

RAG 中向量的作用是做语义检索。

完整流程可以简化成：

```text
文档入库阶段：
文档片段 -> embedding -> 文档向量 -> 存入向量数据库

用户提问阶段：
用户问题 -> embedding -> 问题向量 -> 检索相似文档向量
```

例如知识库里有三段资料：

```text
A：年假申请需要提前 3 个工作日提交。
B：婚假为 10 天，申请时需要提交结婚证复印件。
C：报销发票需要在费用发生后 30 天内提交。
```

用户问：

```text
我请婚假要准备什么？
```

关键词可能没有完全命中“提交材料”这几个字。

但向量检索可以根据语义把 B 找出来。

这就是向量数据库在 RAG 里的核心价值：

```text
不只按字面匹配，而是按语义相似度找资料。
```

### 7. 向量数据库存的是什么？

向量数据库不是把“模型知识”存进去。

它主要存：

```text
文档片段内容
文档片段对应的向量
文档来源
文档 ID
chunk ID
标题
权限
时间
标签
其他 metadata
```

可以理解成：

```text
普通数据库：擅长按字段精确查询。
向量数据库：擅长按语义相似度查询。
```

例如普通数据库适合查：

```sql
where document_id = 'doc_001'
```

向量数据库适合查：

```text
找出和“婚假材料”语义最接近的 5 个文档片段。
```

所以向量数据库不是替代所有数据库。

它通常和业务数据库、文件存储、搜索引擎一起使用。

### 8. 向量相似不等于答案正确

这一点非常重要。

向量检索找到的是“相似内容”，不是“真理”。

它可能出错：

- 用户问题太模糊。
- 文档切分不合理。
- 文档本身过期。
- 相似片段很多，但真正答案在别处。
- 关键词、编号、日期等精确信息没有匹配好。
- embedding 模型不适合当前领域。

例如用户问：

```text
Apple 售后政策是什么？
```

如果知识库里同时有：

```text
苹果水果采购标准
Apple 公司售后政策
```

向量模型需要结合上下文判断 Apple 是公司还是水果。

如果上下文不足，就可能召回错误片段。

所以真实 RAG 系统通常会组合：

```text
向量检索
关键词检索
metadata 过滤
rerank 重排
权限过滤
Prompt 约束
引用来源
质量评估
```

### 9. 面试里怎么解释向量？

可以这样说：

```text
向量本质上是一组有顺序的数字。
在 AI 场景里，embedding 模型会把文本、图片等数据编码成高维向量。
这些向量可以表达语义特征，语义越接近，向量距离通常越近。
所以在 RAG 里，我们会把用户问题和文档片段都转成向量，再通过相似度计算召回相关资料。
```

更短一点：

```text
向量就是语义的数字坐标。
向量数据库就是用这些坐标来做相似度检索。
```

### 10. 本节小结

这一节先记住四句话：

```text
1. 向量是一组有顺序的数字。
2. AI 用向量把语义变成可计算对象。
3. 语义相近的内容，向量距离通常更近。
4. RAG 用向量检索相关资料，但相似不等于一定正确。
```

下一节会进入：

```text
点乘查询机制
```

也就是系统到底如何用数学方式判断两个向量是否相似。

## 02 点乘查询机制

上一节我们说：

```text
向量是语义的数字坐标。
```

那向量数据库怎么判断两个向量像不像？

一种常见方法就是点乘，也叫 dot product。

先记一句最直观的话：

```text
点乘 = 两个向量逐位相乘，再把结果加起来。
```

例如有两个 3 维向量：

```text
A = [1, 2, 3]
B = [4, 5, 6]
```

点乘计算就是：

```text
A · B = 1*4 + 2*5 + 3*6
      = 4 + 10 + 18
      = 32
```

所以点乘不是神秘算法。

它就是一种把两个向量压成一个分数的方法。

这个分数可以用来表示：

```text
两个向量方向是否接近。
两个语义表示是否相似。
```

### 1. 为什么点乘能表示相似度？

看一个简化例子。

假设我们用两个维度描述文本：

```text
第 1 维：请假相关
第 2 维：材料相关
```

用户问题：

```text
请婚假需要什么材料？
```

可以简化成：

```text
query = [0.8, 0.6]
```

知识库里有两个文档片段：

```text
docA = [0.75, 0.65]  婚假申请需要提交结婚证复印件
docB = [-0.3, 0.2]   报销发票需要在 30 天内提交
```

计算 query 和 docA：

```text
0.8*0.75 + 0.6*0.65
= 0.60 + 0.39
= 0.99
```

计算 query 和 docB：

```text
0.8*(-0.3) + 0.6*0.2
= -0.24 + 0.12
= -0.12
```

docA 的分数更高。

所以系统会认为：

```text
docA 比 docB 更接近用户问题。
```

这就是点乘查询的基本直觉。

### 2. 点乘在向量数据库里怎么用？

在 RAG 里，向量数据库通常会做这样的事情：

```text
1. 用户问题转成 query_vector
2. 取出知识库里的 document_vectors
3. 分别计算 query_vector 和每个 document_vector 的点乘分数
4. 按分数从高到低排序
5. 返回 top_k 个最相关片段
```

伪代码可以这样理解：

```text
query_vector = embed("请婚假需要什么材料？")

scores = []

for chunk in vector_database:
    score = dot(query_vector, chunk.vector)
    scores.append({ chunk, score })

return top_k(scores)
```

返回结果可能像这样：

| 文档片段 | 点乘分数 | 是否应该优先返回 |
| --- | ---: | --- |
| 婚假申请需提交结婚证复印件 | 0.91 | 是 |
| 年假申请需提前 3 个工作日 | 0.62 | 可能相关 |
| 报销发票需 30 天内提交 | 0.13 | 否 |

这就是向量查询的核心：

```text
把问题向量和文档向量逐个打分，再按分数排序。
```

### 3. 点乘看的是方向还是长度？

这里要稍微注意一个细节。

点乘分数会受两个因素影响：

- 向量方向。
- 向量长度。

如果两个向量方向接近，点乘通常会更大。

但如果某个向量本身特别长，也可能把点乘分数拉高。

所以很多向量检索系统会先做归一化：

```text
把向量长度统一到 1。
```

归一化之后，点乘就更接近我们常说的余弦相似度。

可以简单理解为：

```text
未归一化点乘：方向 + 长度都会影响分数。
归一化点乘：主要看方向是否接近。
```

学习阶段先不用被“余弦相似度”吓到。

记住：

```text
很多 embedding 检索里，归一化后的点乘可以用来衡量语义相似度。
```

### 4. 点乘分数越高，一定越好吗？

不一定。

点乘分数高，只说明：

```text
两个向量在当前 embedding 空间里更相似。
```

但它不保证：

- 文档一定是正确答案。
- 文档一定没有过期。
- 文档一定有用户权限。
- 文档一定覆盖了完整上下文。
- 模型最终一定会基于它回答。

例如用户问：

```text
婚假需要什么材料？
```

系统可能召回：

```text
婚假申请流程
婚假天数规定
婚假材料说明
```

这三段都和婚假相关。

但真正回答“材料”的可能只有第三段。

所以真实系统常常会在点乘召回之后再做：

```text
metadata 过滤
关键词补充召回
rerank 重排
上下文拼接
引用来源
```

点乘解决的是第一步：

```text
先从大量文档里粗略找出可能相关的内容。
```

### 5. 点乘、距离、相似度的关系

初学时经常会混淆三个词：

- 点乘。
- 距离。
- 相似度。

可以这样理解：

```text
点乘：一种相似度打分方法，分数越高通常越相似。
距离：两个向量离得多远，距离越小通常越相似。
相似度：更宽泛的概念，可以用点乘、余弦、欧氏距离等方式计算。
```

不同向量数据库会支持不同的度量方式：

| 度量方式 | 直觉 |
| --- | --- |
| dot product | 点乘分数越高越相似 |
| cosine similarity | 方向越接近越相似 |
| Euclidean distance | 距离越短越相似 |

课程这一节先重点理解点乘。

后面再看向量数据库索引、维度、长文本切片时，会更容易串起来。

### 6. 面试里怎么解释点乘查询？

可以这样说：

```text
点乘查询就是把用户问题向量和知识库里的文档向量逐位相乘再求和，得到一个相似度分数。
向量数据库会对候选文档计算这个分数，然后按分数排序，返回 top_k 个最相关片段。
在实际 RAG 系统里，点乘通常只是召回阶段的一部分，后面还会结合过滤、重排、权限和 Prompt 约束来提高答案质量。
```

更短一点：

```text
点乘就是给两个向量算相似度分数。
分数越高，系统越认为这段资料和用户问题相关。
```

### 7. 本节小结

这一节记住四句话：

```text
1. 点乘就是两个向量逐位相乘再相加。
2. 点乘可以把两个向量的相似程度变成一个分数。
3. 向量数据库会用这个分数排序并返回 top_k 结果。
4. 点乘高只代表可能相关，真实 RAG 还要过滤、重排和校验。
```

## 03 向量数据库的索引机制

上一节讲点乘时，我们用了一个很直接的思路：

```text
用户问题向量
  ↓
和知识库里每一个文档向量计算相似度
  ↓
按分数排序
  ↓
返回 top_k
```

这个思路在数据量很小时没问题。

但真实知识库可能有：

```text
10 万个 chunk
100 万个 chunk
1000 万个 chunk
```

如果每次查询都和所有向量做一遍点乘，成本会非常高。

所以向量数据库需要索引。

一句话理解：

```text
索引就是提前组织数据，让查询时不用全量扫描。
```

### 1. 没有索引会发生什么？

假设知识库里有 100 万个文档片段。

用户问：

```text
请婚假需要什么材料？
```

系统把问题转成向量之后，如果没有索引，就要：

```text
query_vector 和第 1 个 chunk 向量算相似度
query_vector 和第 2 个 chunk 向量算相似度
query_vector 和第 3 个 chunk 向量算相似度
...
query_vector 和第 1000000 个 chunk 向量算相似度
```

这叫暴力搜索，也可以叫 full scan。

优点是：

```text
理论上最准确。
```

缺点是：

```text
数据量大时太慢。
```

所以真实向量数据库通常不会每次都扫全库。

它会提前建立索引，让查询时更快定位可能相近的向量。

### 2. 普通数据库索引和向量索引的区别

普通数据库经常按字段查：

```sql
where user_id = 123
where created_at > '2026-01-01'
where status = 'paid'
```

这种查询目标很明确：

```text
找到字段值等于某个值的数据。
```

所以普通索引通常围绕字段值组织。

向量数据库查的是：

```text
找出和这个 query_vector 最相似的 top_k 个向量。
```

它不是精确等值查询，而是近邻查询。

也就是：

```text
在高维空间里，找离我最近的一批点。
```

所以向量索引的核心目标是：

```text
更快找到近邻向量。
```

### 3. 向量索引通常做的是近似搜索

这里有一个非常重要的工程取舍：

```text
向量数据库经常使用近似最近邻搜索。
```

英文叫 ANN：

```text
Approximate Nearest Neighbor
```

意思是：

```text
不一定保证找到全库里绝对最相似的那几个，
但尽量快速找到足够相似的一批。
```

为什么要近似？

因为在大规模高维向量里，如果每次都追求绝对精确，速度会很慢。

而 RAG 场景里，我们通常不是只要唯一一个结果，而是取：

```text
top_k = 5
top_k = 10
top_k = 20
```

只要召回结果足够相关，后面还可以交给 reranker 和 LLM 继续处理。

所以向量检索常见取舍是：

```text
用一点点精度损失，换更低延迟和更高吞吐。
```

### 4. 索引机制可以怎么理解？

可以用图书馆做类比。

如果没有索引，你要找一本和“婚假材料”相关的书，就只能一本一本翻。

有了索引之后，图书馆会提前把书组织起来：

```text
人事制度类
财务报销类
合同法务类
产品说明类
```

你要找婚假材料，就优先去人事制度类附近找。

向量数据库也类似。

它会提前根据向量之间的空间关系建立结构，让查询时先去“可能相关的区域”找，而不是全库乱扫。

### 5. 常见向量索引类型

学习阶段不需要把所有细节背下来。

先知道几个常见名字：

| 索引类型 | 核心直觉 |
| --- | --- |
| Flat | 不建复杂索引，暴力算全量相似度 |
| HNSW | 建一张多层近邻图，查询时沿着图快速靠近目标 |
| IVF | 先把向量分成多个簇，查询时只搜相关簇 |
| PQ | 对向量做压缩，减少存储和计算成本 |
| IVF-PQ | 先聚类再压缩，常用于更大规模数据 |

最容易理解的是三类：

```text
Flat：全量扫描，准但慢。
HNSW：像地图导航，通过近邻图快速找相似点。
IVF：像先分区，再只查相关分区。
```

### 6. HNSW 的直觉

HNSW 可以先理解成：

```text
给向量之间建立一张“朋友关系图”。
```

语义相近的向量会互相连接。

查询时，系统不是从所有点里逐个比较，而是在图上跳转：

```text
先找到一个入口点
  ↓
看它附近哪些点更接近 query
  ↓
不断往更相似的方向移动
  ↓
最后停在一批最相似的点附近
```

它有点像在城市里找目的地：

```text
不用逐个检查每栋楼；
而是先走主干道，再进入附近街区，最后找到目标区域。
```

HNSW 的常见特点：

- 查询速度快。
- 召回效果通常不错。
- 内存占用相对较高。
- 构建索引需要一定成本。

很多向量数据库默认或推荐 HNSW，是因为它在中大规模语义检索里很好用。

### 7. IVF 的直觉

IVF 可以先理解成：

```text
先把向量空间分成很多区域。
```

比如把 100 万个向量分成 1000 个簇。

每个簇都有一个中心点。

查询时先判断：

```text
query_vector 更靠近哪些簇中心？
```

然后只在这些簇里面找相似向量。

这样就不用扫全部 100 万个向量。

例如：

```text
全库：1000000 个向量
分成：1000 个簇
查询时只查：最相关的 10 个簇
```

实际比较的候选数量就会大幅减少。

IVF 的常见特点：

- 适合更大规模数据。
- 查询速度快。
- 需要训练或构建聚类中心。
- 如果查的簇太少，可能漏掉真正相关的向量。

### 8. 索引参数影响什么？

向量索引不是建完就万事大吉。

它通常有一些参数会影响效果：

```text
召回率
查询速度
内存占用
构建时间
写入成本
```

比如：

```text
HNSW 搜得更深：召回更好，但查询更慢。
IVF 查更多簇：召回更好，但查询更慢。
top_k 更大：返回更多候选，但后续 rerank 和 LLM 成本更高。
```

所以向量索引调优本质上是在做权衡：

```text
更准
更快
更省资源
```

这三者很难同时拉满。

### 9. RAG 里如何选择索引？

学习阶段可以先用简单判断：

| 数据规模 | 可选思路 |
| --- | --- |
| 几千到几万 chunk | Flat 或默认索引通常够用 |
| 几十万到几百万 chunk | HNSW 很常见 |
| 上千万级别以上 | IVF、PQ、分片、混合检索更常见 |

但真实项目不应该只按数据量拍脑袋。

还要看：

- 查询延迟要求。
- 内存预算。
- 写入更新频率。
- embedding 维度。
- top_k 数量。
- 是否需要 metadata 过滤。
- 是否有 reranker。
- 是否需要多租户和权限隔离。

例如企业知识库文档不多，但权限复杂。

这时索引不是唯一重点，metadata 过滤和权限隔离也很关键。

### 10. 索引不是 RAG 效果的全部

索引主要解决：

```text
查得快。
```

但 RAG 还要解决：

```text
查得准。
答得对。
能追溯。
不越权。
```

如果文档切分很差，索引再高级也救不了全部问题。

如果 embedding 模型不适合业务领域，索引只能更快地找到“不太对”的向量。

如果没有 rerank，top_k 里可能混入很多看似相关但不能回答问题的片段。

所以要把索引放回完整链路里看：

```text
文档质量
  ↓
切分策略
  ↓
embedding 模型
  ↓
向量索引
  ↓
检索参数
  ↓
rerank
  ↓
Prompt 和生成
```

索引是加速器，不是魔法。

### 11. 面试里怎么解释向量索引？

可以这样说：

```text
向量数据库的索引机制，是为了避免查询时对全量向量逐个计算相似度。
它会提前按照向量空间关系组织数据，让系统可以更快找到和 query 向量接近的候选向量。
常见索引包括 Flat、HNSW、IVF、PQ 等，工程上需要在召回率、查询延迟、内存占用和构建成本之间做权衡。
```

更短一点：

```text
向量索引就是为了让相似向量查得更快。
```

### 12. 本节小结

这一节记住五句话：

```text
1. 没有索引就要全量扫描，数据大时会很慢。
2. 向量索引用来快速找到近邻向量。
3. 大规模向量检索常用近似最近邻搜索。
4. HNSW 像近邻图导航，IVF 像先分区再查询。
5. 索引主要解决速度问题，RAG 效果还取决于切分、embedding、rerank 和 Prompt。
```

## 04 数据最终变成向量的产物与特征

前面几节我们一直在说：

```text
文本会变成向量。
```

但在真实工程里，数据向量化之后，产物不只是“一串数字”。

更准确地说，向量化之后会得到一条可检索的数据记录。

它通常包含：

```text
原始内容
向量
向量维度
embedding 模型
文档来源
chunk 信息
metadata
权限信息
创建时间
```

也就是说：

```text
向量是核心，但不是全部。
```

### 1. 一个向量化结果长什么样？

假设原始文档里有一段：

```text
婚假为 10 天，申请时需要提交结婚证复印件。
```

经过切分和 embedding 之后，可能会存成类似这样的结构：

```json
{
  "id": "chunk_policy_001_003",
  "documentId": "policy_001",
  "content": "婚假为 10 天，申请时需要提交结婚证复印件。",
  "vector": [0.031, -0.128, 0.556, 0.204],
  "embeddingModel": "text-embedding-model",
  "dimension": 4,
  "metadata": {
    "source": "员工手册",
    "chapter": "请假制度",
    "permission": "internal",
    "chunkIndex": 3
  }
}
```

真实向量不会只有 4 维，这里只是为了方便展示。

真实数据可能是：

```text
384 维
768 维
1024 维
1536 维
3072 维
```

甚至更高。

但工程结构大体类似。

### 2. 向量本身有什么特征？

向量本身通常有几个重要特征。

第一，向量是数字数组。

例如：

```text
[0.031, -0.128, 0.556, ..., 0.204]
```

第二，向量有固定维度。

同一个向量库、同一个索引里，通常要求所有向量维度一致。

不能一条是 768 维，另一条是 1536 维。

因为相似度计算要求逐位计算：

```text
query[0] * doc[0]
query[1] * doc[1]
...
```

如果维度不一样，就没法直接点乘。

第三，向量一般是浮点数。

也就是：

```text
0.031
-0.128
0.556
```

这些数不是人工填的，而是 embedding 模型输出的。

第四，向量通常不能直接被人解释。

我们很难说：

```text
第 327 维一定代表“婚假”。
```

真实向量维度是模型学出来的隐含特征。

### 3. embedding 模型决定向量空间

这一点特别重要：

```text
不同 embedding 模型生成的向量，不能随便混在一起比较。
```

因为每个模型都有自己的向量空间。

同一句话：

```text
婚假需要什么材料？
```

用模型 A 生成的向量，和用模型 B 生成的向量，数字分布可能完全不同。

如果文档用模型 A 入库，查询时却用模型 B 生成 query 向量，就可能出现严重问题：

```text
文档向量和问题向量不在同一个语义空间里。
```

这就像：

```text
一个地图用北京坐标系；
另一个地图用上海坐标系；
直接比较位置会乱。
```

所以 RAG 系统里要记录：

```text
embeddingModel
dimension
createdAt
version
```

当更换 embedding 模型时，通常需要重新向量化已有文档。

### 4. 向量表达的是语义特征

数据变成向量之后，不是变成了关键词列表。

它变成的是一种语义表示。

例如：

```text
请婚假需要什么材料？
婚假申请需要提交结婚证复印件。
```

这两句话字面并不完全一样。

但它们可能在向量空间里比较接近，因为都包含：

```text
婚假
申请
材料
证明
制度问答
```

向量的优势就是能捕捉这种语义接近。

但它也有弱点。

例如：

```text
订单号 A12345 的状态是什么？
```

这类问题更像精确查询。

如果只靠语义向量，可能不如直接查数据库：

```sql
where order_id = 'A12345'
```

所以向量表达的是语义特征，不是万能查询能力。

### 5. metadata 是向量检索的关键补充

真实向量库里不能只存 vector。

还要存 metadata。

metadata 可以包括：

- 文档来源。
- 文档标题。
- 章节。
- chunk 序号。
- 用户或部门权限。
- 创建时间。
- 更新时间。
- 业务类型。
- 语言。
- 标签。

为什么 metadata 重要？

因为很多查询不能只靠语义相似度。

例如：

```text
只查 HR 制度文档。
只查 2026 年之后更新的文档。
只查当前用户有权限看的文档。
只查某个产品线的说明书。
```

这时就需要：

```text
向量相似度 + metadata 过滤
```

典型流程是：

```text
先按权限、类型、时间过滤候选范围；
再在候选范围里做向量相似度检索。
```

或者：

```text
先向量召回一批候选；
再根据 metadata 过滤和重排。
```

具体顺序要看数据库能力和业务需求。

### 6. chunk 信息决定可追溯性

RAG 里非常重要的一点是：

```text
检索结果要能追溯回原文。
```

所以每个向量不应该只是：

```text
vector = [...]
```

还应该知道：

```text
这个向量来自哪个文档？
来自第几章？
来自第几个 chunk？
原始文本是什么？
前后文在哪里？
```

否则模型生成答案后，你无法回答：

```text
这句话依据哪里？
为什么召回这段？
原文是否真的这么说？
```

一个成熟 RAG 系统通常会保存：

```text
documentId
chunkId
chunkIndex
content
source
startOffset
endOffset
```

这些信息让系统可以返回引用来源，也方便排查错误。

### 7. 向量化产物会影响存储成本

向量是数字数组，会占用存储空间。

假设：

```text
一个向量 1536 维
每个维度用 float32 存储，约 4 字节
```

那么一个向量大约：

```text
1536 * 4 = 6144 字节 ≈ 6 KB
```

如果有 100 万个 chunk：

```text
6 KB * 1000000 ≈ 6 GB
```

这还只是向量本身。

还没算：

- 原文内容。
- metadata。
- 索引结构。
- 副本。
- 日志。
- 压缩或量化前后的额外数据。

所以向量维度、chunk 数量、索引类型都会影响成本。

这也是为什么后面会讨论：

```text
向量维度是越多越好吗？
一本 10w 字的书如何向量化？
大量短句如何向量化？
```

### 8. 向量化产物会影响检索效果

同一份数据，向量化效果会受很多因素影响：

- 原始文本质量。
- 文档解析是否正确。
- chunk 切分是否合理。
- embedding 模型是否适合领域。
- 是否保留标题和章节信息。
- 是否把表格、代码、图片说明处理好。
- 是否混入噪声文本。

例如两个 chunk：

```text
chunk A：婚假为 10 天，申请时需要提交结婚证复印件。
chunk B：婚假。
```

chunk B 太短，语义信息不足。

它生成的向量可能不够稳定。

再比如：

```text
chunk C：本制度适用于所有正式员工。请假分为年假、病假、婚假、产假、事假、调休假，具体规则如下……
```

chunk C 太大，里面包含太多主题。

它生成的向量可能不够聚焦。

所以向量化产物质量，很大程度由上游处理决定。

### 9. 查询结果里 score 是什么？

向量检索返回时，通常会带一个 score。

例如：

```json
{
  "chunkId": "policy_001_003",
  "content": "婚假为 10 天，申请时需要提交结婚证复印件。",
  "score": 0.91,
  "metadata": {
    "source": "员工手册"
  }
}
```

这个 score 通常表示：

```text
query 向量和 chunk 向量的相似度或距离。
```

但要注意：

```text
不同数据库、不同度量方式，score 含义可能不同。
```

有的系统分数越高越相似：

```text
dot product
cosine similarity
```

有的系统距离越小越相似：

```text
Euclidean distance
```

所以不能只看 score 数字大小。

要先确认：

```text
当前使用的 distance metric 是什么？
分数越高越好，还是越低越好？
是否做过归一化？
```

### 10. 面试里怎么解释向量化产物？

可以这样说：

```text
数据向量化之后，核心产物是一条可检索的 embedding 记录。
它不仅包含高维向量本身，还应该包含原始 chunk 内容、文档来源、chunkId、metadata、权限信息、embedding 模型和向量维度。
向量用于相似度计算，metadata 和来源信息用于过滤、权限控制、引用追溯和问题排查。
```

更短一点：

```text
向量化不是只得到一串数字，而是得到一条带语义向量和上下文信息的检索记录。
```

### 11. 本节小结

这一节记住五句话：

```text
1. 向量化产物不只是 vector，还包括 content、metadata、source 等信息。
2. 同一个索引里的向量维度必须一致。
3. 文档和 query 应该使用同一个 embedding 模型和向量空间。
4. metadata 用于过滤、权限、分类和追溯。
5. 向量化质量取决于原始数据、切分策略和 embedding 模型。
```

## 05 数据转化向量的核心算法

这一节要回答一个关键问题：

```text
数据到底是怎么变成向量的？
```

先给出一个学习版答案：

```text
数据转向量的核心，是用 embedding 模型把原始数据编码成高维数字表示。
```

如果是文本，大致流程是：

```text
文本
  ↓
分词 / tokenization
  ↓
token embedding
  ↓
神经网络编码
  ↓
pooling 聚合
  ↓
归一化
  ↓
最终向量
```

这个过程不需要我们手写每个维度的数字。

我们调用 embedding 模型，模型内部完成编码。

### 1. 为什么不能直接手写规则？

假设要把下面两句话转成向量：

```text
怎么退钱？
退款流程说明。
```

如果靠人工规则，我们可能会写：

```text
退钱 = 退款
```

但真实语言太复杂。

用户可能会说：

```text
钱能不能退？
我不想买了怎么处理？
订单取消后多久到账？
售后退款入口在哪里？
```

这些表达字面不同，但语义相关。

靠人工枚举同义词和规则，很快就维护不动。

embedding 模型的价值就是：

```text
从大量数据中学习语义关系，
自动把语义接近的表达映射到相近的向量位置。
```

### 2. 早期方法：one-hot、词袋、TF-IDF

在深度学习 embedding 普及之前，也有一些把文本变成数字的方法。

第一种是 one-hot。

例如词表里有 5 个词：

```text
猫、狗、汽车、退款、发票
```

可以表示成：

```text
猫   = [1, 0, 0, 0, 0]
狗   = [0, 1, 0, 0, 0]
汽车 = [0, 0, 1, 0, 0]
```

问题是：

```text
每个词之间看起来都一样远。
```

one-hot 不知道猫和狗更接近，也不知道退款和退钱有关。

第二种是词袋模型。

它会统计一段文本里出现了哪些词。

例如：

```text
退款流程说明
```

可以表示成：

```text
退款: 1
流程: 1
说明: 1
```

词袋能表示词频，但不太理解语义。

第三种是 TF-IDF。

它会给重要词更高权重，给到处都出现的普通词更低权重。

例如：

```text
退款、发票、婚假
```

可能比：

```text
的、是、一个、可以
```

更有区分度。

TF-IDF 对关键词搜索很有用，但它仍然偏字面匹配。

它不天然理解：

```text
退钱 ≈ 退款
请假材料 ≈ 提交证明
```

### 3. 神经网络 embedding 的核心变化

现代 embedding 模型不再只是统计词频。

它会学习：

```text
哪些词经常出现在相似上下文里？
哪些句子表达的是相似意图？
哪些文本应该在向量空间里靠近？
哪些文本应该远离？
```

早期有 Word2Vec 这类方法。

它的核心直觉可以简化为：

```text
一个词的含义，可以由它周围经常出现的词来刻画。
```

例如：

```text
猫 会叫
狗 会叫
猫 是宠物
狗 是宠物
```

模型会逐渐学到：

```text
猫 和 狗 在语义空间里应该比较近。
```

这比 one-hot 强很多。

但 Word2Vec 更多是词级别向量。

RAG 里更常用的是句子、段落、文档 chunk 级别的向量。

所以现代系统更多使用基于 Transformer 的 embedding 模型。

### 4. 现代文本 embedding 的基本流程

以一句话为例：

```text
婚假需要提交什么材料？
```

第一步：分词。

```text
婚假 / 需要 / 提交 / 什么 / 材料 / ？
```

真实模型会切成 token，不一定完全等于中文词语。

第二步：每个 token 变成初始向量。

```text
婚假 -> token vector A
需要 -> token vector B
提交 -> token vector C
材料 -> token vector D
```

第三步：这些 token 向量进入神经网络。

如果是 Transformer embedding 模型，内部会通过注意力机制让 token 互相看见上下文关系。

例如：

```text
提交 + 材料
婚假 + 申请
需要 + 什么
```

模型会把这些关系融合进每个 token 的表示。

第四步：把多个 token 的表示合成一个句向量。

这一步叫 pooling。

常见方式包括：

```text
取特殊 token 的表示
对所有 token 表示求平均
加权平均
使用专门的 projection 层
```

第五步：得到最终 embedding 向量。

```text
婚假需要提交什么材料？
  ↓
[0.031, -0.128, 0.556, ..., 0.204]
```

### 5. pooling 为什么重要？

一句话通常有多个 token。

但向量数据库希望每个 chunk 存一条固定长度向量。

所以需要把：

```text
多个 token 向量
```

变成：

```text
一个句子 / 段落向量
```

这就是 pooling 的作用。

可以简单理解为：

```text
把一堆 token 的语义信息压缩成一个整体表示。
```

如果 pooling 做得不好，最终向量就可能不能很好代表整段文本。

例如 chunk 里有很多主题：

```text
年假、婚假、报销、绩效、离职流程……
```

pooling 后的整体向量会比较“杂”。

这也是为什么 RAG 要重视切分策略。

### 6. 对比学习：让相似文本靠近

很多 embedding 模型会通过对比学习来训练。

核心直觉是：

```text
相似的问题和答案，向量距离拉近。
不相关的问题和答案，向量距离推远。
```

例如正样本：

```text
问题：请婚假需要什么材料？
文档：婚假申请需要提交结婚证复印件。
```

模型希望它们的向量更接近。

负样本：

```text
问题：请婚假需要什么材料？
文档：报销发票需要在 30 天内提交。
```

模型希望它们的向量更远。

训练久了之后，模型就学会：

```text
哪些文本应该互相靠近，
哪些文本应该互相远离。
```

所以 embedding 模型不是简单压缩文本。

它是在学习一种适合检索的语义空间。

### 7. 归一化：方便相似度计算

很多 embedding 模型输出向量后，会做归一化。

归一化可以简单理解为：

```text
把向量长度统一。
```

这样做的好处是：

```text
相似度计算更关注方向，而不是向量长度。
```

在很多向量检索里，如果向量已经归一化：

```text
点乘
```

就和：

```text
余弦相似度
```

非常接近。

这也是为什么前面讲点乘时会提到：

```text
点乘分数会受方向和长度影响。
```

归一化就是为了减少长度因素的干扰。

### 8. 文本、图片、音频都可以向量化

向量化不只适用于文本。

不同数据有不同 encoder：

| 数据类型 | 常见编码方式 |
| --- | --- |
| 文本 | tokenizer + text encoder |
| 图片 | image encoder / vision transformer |
| 音频 | audio encoder |
| 视频 | 图像帧、音频、字幕、多模态 encoder |
| 代码 | code encoder / text encoder |

但核心思想类似：

```text
原始数据
  ↓
编码模型
  ↓
高维向量
```

多模态检索里，甚至可以把图片和文字映射到同一个向量空间。

例如：

```text
文字：红色草莓图片
图片：一张草莓照片
```

如果模型训练得好，它们的向量也可以接近。

### 9. embedding 模型和生成模型的区别

这里要区分两类模型：

```text
生成模型：输入 prompt，输出文字。
embedding 模型：输入文本，输出向量。
```

生成模型更像：

```text
写答案、做推理、生成内容。
```

embedding 模型更像：

```text
把内容变成适合检索的语义坐标。
```

在 RAG 里，两者经常配合：

```text
embedding 模型：负责找资料。
LLM 生成模型：负责读资料并回答。
```

所以不要把 embedding 模型理解成“低配 LLM”。

它的目标不同：

```text
embedding 模型追求检索相似度好。
生成模型追求输出答案质量好。
```

### 10. 工程上如何调用 embedding？

实际代码里通常不是自己实现 Transformer。

而是调用模型 API 或本地 embedding 模型：

```text
input:  ["婚假需要提交什么材料？"]
output: [[0.031, -0.128, 0.556, ..., 0.204]]
```

伪代码可以这样理解：

```text
chunks = split(document)

for chunk in chunks:
    vector = embedding_model.embed(chunk.content)
    vector_db.insert({
        id: chunk.id,
        content: chunk.content,
        vector: vector,
        metadata: chunk.metadata
    })
```

查询时也是同一个逻辑：

```text
query_vector = embedding_model.embed(user_question)
results = vector_db.search(query_vector, top_k=5)
```

关键要求是：

```text
文档入库和用户查询要使用同一个 embedding 模型。
```

### 11. 影响向量质量的关键因素

数据转向量不是只看模型。

以下因素都会影响最终检索效果：

- 原始文本是否干净。
- 文档解析有没有乱码。
- chunk 是否语义完整。
- 是否保留标题和章节。
- embedding 模型是否适合中文和业务领域。
- 文档和 query 是否使用同一个模型。
- 是否做归一化。
- 是否混入大量无意义模板文本。
- 是否需要领域词表或业务同义词补充。

例如：

```text
婚假材料
```

如果 chunk 只写：

```text
见附件。
```

就算 embedding 模型再强，也很难生成有用向量。

因为输入本身没有足够语义。

### 12. 面试里怎么解释核心算法？

可以这样说：

```text
数据转向量的核心是 embedding 编码。以文本为例，系统会先把文本分成 token，再把 token 映射成初始向量，然后通过 Transformer 等神经网络融合上下文语义，最后通过 pooling 把多个 token 表示聚合成一个固定维度的句向量或段落向量。很多 embedding 模型会通过对比学习训练，让语义相近的文本向量更近、不相关文本向量更远，从而适合向量检索。
```

更短一点：

```text
embedding 模型把数据编码成高维语义向量；训练目标是让相似内容更近、不相关内容更远。
```

### 13. 本节小结

这一节记住五句话：

```text
1. 数据转向量的核心是 embedding 模型编码。
2. 文本 embedding 通常经历分词、token embedding、神经网络编码、pooling 和归一化。
3. 对比学习会让相似文本靠近、不相关文本远离。
4. embedding 模型负责检索表示，生成模型负责生成答案。
5. 向量质量不仅取决于模型，也取决于清洗、切分、标题、metadata 和业务领域。
```

## 06 向量查询点乘算法机制

第 02 节已经讲过点乘的基本直觉：

```text
两个向量逐位相乘，再把结果加起来。
```

这一节把它放到完整查询流程里看。

向量查询的核心问题是：

```text
给定一个用户问题向量 query_vector，
如何从大量文档向量里找出最相似的 top_k 个？
```

如果使用点乘作为相似度算法，那么完整机制可以简化成：

```text
1. 用户问题转成 query 向量
2. 取出候选文档向量
3. query 和每个候选向量做点乘
4. 得到每个候选的 score
5. 按 score 从高到低排序
6. 返回 top_k 个结果
```

### 1. 点乘公式

假设有两个向量：

```text
q = [q1, q2, q3, ..., qm]
x = [x1, x2, x3, ..., xm]
```

它们的点乘是：

```text
q · x = q1*x1 + q2*x2 + q3*x3 + ... + qm*xm
```

其中：

```text
q = query 向量
x = document chunk 向量
m = 向量维度数量
```

为了避免符号混淆，也可以写成：

```text
score(query, chunk) = sum(query[i] * chunk[i])
```

这就是点乘相似度的基本计算。

### 2. 逐维贡献怎么理解？

看一个简化例子。

假设向量有 4 个维度：

```text
第 1 维：请假制度
第 2 维：材料证明
第 3 维：报销财务
第 4 维：技术文档
```

用户问题：

```text
婚假需要提交什么材料？
```

query 向量可以简化成：

```text
query = [0.8, 0.7, 0.1, 0.0]
```

文档 A：

```text
婚假申请需要提交结婚证复印件。
docA = [0.9, 0.8, 0.0, 0.0]
```

文档 B：

```text
报销发票需要在 30 天内提交。
docB = [0.1, 0.2, 0.9, 0.0]
```

计算 query 和 docA：

```text
0.8*0.9 + 0.7*0.8 + 0.1*0.0 + 0.0*0.0
= 0.72 + 0.56 + 0 + 0
= 1.28
```

计算 query 和 docB：

```text
0.8*0.1 + 0.7*0.2 + 0.1*0.9 + 0.0*0.0
= 0.08 + 0.14 + 0.09 + 0
= 0.31
```

docA 分数更高。

因为 query 和 docA 在“请假制度”“材料证明”这些维度上同时较高。

这就是点乘的直觉：

```text
两个向量在相同方向上越一致，累加出来的分数越高。
```

### 3. 正数、负数和方向

真实向量里会有正数和负数。

如果两个维度同号：

```text
正 * 正 = 正
负 * 负 = 正
```

它们会给总分加分。

如果两个维度异号：

```text
正 * 负 = 负
负 * 正 = 负
```

它们会给总分扣分。

可以简单理解为：

```text
方向一致：加分。
方向相反：扣分。
没什么关系：贡献接近 0。
```

所以点乘不是只看某一个关键词，而是把所有维度的关系综合成一个分数。

### 4. 批量查询的矩阵形式

真实向量库不会只比较一条文档。

它会面对很多文档向量。

假设：

```text
query 向量维度 = d
文档数量 = n
```

文档向量可以组成一个矩阵：

```text
documents = [
  doc1,
  doc2,
  doc3,
  ...
  docn
]
```

每个 doc 都是 d 维。

点乘查询可以写成：

```text
scores = documents * query
```

也就是一次性算出：

```text
doc1 · query
doc2 · query
doc3 · query
...
docn · query
```

这就是为什么向量计算很适合用矩阵运算、SIMD、GPU 或高性能数值库加速。

底层看起来是很多点乘，本质上是一批矩阵乘法。

### 5. top_k 排序机制

计算出 score 后，系统不会把所有结果都返回。

它会取分数最高的前 k 个。

例如：

```text
top_k = 3
```

候选结果：

| chunk | score |
| --- | ---: |
| chunk_001 婚假材料 | 0.92 |
| chunk_017 婚假天数 | 0.81 |
| chunk_032 请假流程 | 0.76 |
| chunk_044 报销制度 | 0.21 |
| chunk_051 技术规范 | -0.03 |

返回：

```text
chunk_001
chunk_017
chunk_032
```

这就是 top_k。

在 RAG 里，top_k 不能随便设。

太小：

```text
可能漏掉真正有用的片段。
```

太大：

```text
会带入噪声，增加 rerank 和 LLM 上下文成本。
```

常见做法是：

```text
先召回较多候选，再 rerank 精排，最后只放少量高质量片段进 Prompt。
```

### 6. score 阈值机制

除了 top_k，有些系统还会设置相似度阈值。

例如：

```text
score >= 0.75 才认为可用
```

这样可以避免把明显不相关的内容塞给模型。

但阈值也不能乱设。

阈值太高：

```text
可能导致很多问题检索不到内容。
```

阈值太低：

```text
可能把不相关片段也放进 Prompt。
```

所以阈值通常要通过测试集调出来。

例如准备一组常见问题：

```text
婚假材料怎么提交？
报销发票过期怎么办？
试用期离职流程是什么？
```

观察正确文档的 score 分布，再决定阈值。

### 7. 点乘和归一化的关系

如果向量没有归一化，点乘会受向量长度影响。

例如：

```text
A = [1, 0]
B = [10, 0]
C = [0.8, 0.6]
```

A 和 B 方向完全一样，但 B 更长。

点乘时，长向量可能天然更占优势。

所以很多检索系统会先做归一化：

```text
把每个向量缩放到长度为 1。
```

归一化后：

```text
点乘更接近比较方向。
```

也就是：

```text
两个向量方向越接近，分数越高。
```

在语义检索里，我们往往更关心方向是否接近，而不是向量长度本身。

### 8. 点乘查询和索引如何配合？

第 03 节讲过索引机制。

真实向量数据库通常不会对全库直接点乘。

更常见的是：

```text
1. 用索引快速找到一批候选向量
2. 对候选向量计算点乘或近似点乘
3. 维护一个 top_k 结果集合
4. 返回分数最高的结果
```

也就是说：

```text
索引负责缩小搜索范围。
点乘负责给候选结果打分。
top_k 负责筛出最终结果。
```

如果使用 HNSW，可以理解成：

```text
在近邻图上移动时，不断用点乘判断哪个邻居更接近 query。
```

如果使用 IVF，可以理解成：

```text
先找到 query 最接近的几个簇，再在这些簇里做点乘排序。
```

所以点乘不是和索引对立。

它经常是索引搜索过程中的打分函数。

### 9. 一次完整查询可以这样理解

以用户问题为例：

```text
婚假需要提交什么材料？
```

完整流程：

```text
1. embedding_model.embed(question)
   得到 query_vector

2. vector_db.search(query_vector, top_k=5)
   使用索引找到候选向量

3. 对候选向量计算 dot product score
   得到相似度分数

4. 按 score 排序
   返回最相关 chunks

5. RAG Service 把 chunks 放进 Prompt
   让 LLM 基于资料回答
```

伪代码：

```text
query_vector = embed(user_question)

candidates = index.search(query_vector)

scored = []
for chunk in candidates:
    score = dot(query_vector, chunk.vector)
    scored.append({ chunk, score })

results = sort_by_score_desc(scored).take(top_k)

answer = llm.generate(user_question, results)
```

### 10. 点乘查询的常见问题

第一，维度不一致。

```text
query 是 1024 维，doc 是 1536 维。
```

这种不能直接点乘。

通常说明：

```text
文档和查询用了不同 embedding 模型。
```

第二，分数解释错。

有些数据库返回的是 similarity，越高越好。

有些数据库返回的是 distance，越低越好。

要先看清楚 metric。

第三，只看分数不看内容。

点乘分数高不代表文档一定能回答问题。

还要看：

```text
content 是否完整
source 是否可信
metadata 是否匹配
用户是否有权限
```

第四，只用向量不用关键词。

对于编号、代码、订单号、日期、法律条款号这类精确信息，关键词或结构化查询经常更可靠。

### 11. 面试里怎么解释向量查询点乘算法？

可以这样说：

```text
向量查询中的点乘算法，是把用户问题向量和候选文档向量按维度逐位相乘并求和，得到一个相似度 score。向量数据库会对候选向量计算这个 score，然后按 score 排序返回 top_k。工程上通常会先用 HNSW、IVF 等索引缩小候选范围，再用点乘作为打分函数；如果向量做过归一化，点乘基本就等价于比较向量方向，也接近余弦相似度。
```

更短一点：

```text
点乘算法就是给 query 向量和文档向量打相似度分，分数越高越优先召回。
```

### 12. 本节小结

这一节记住五句话：

```text
1. 点乘公式是 sum(query[i] * doc[i])。
2. 同方向维度会加分，反方向维度会扣分。
3. 向量库会用 score 排序并返回 top_k。
4. 归一化后，点乘更接近比较语义方向。
5. 真实系统通常是索引缩小范围，点乘打分，rerank 再精排。
```

## 07 向量维度是越多越好吗？

先给结论：

```text
不是。
```

向量维度更多，通常代表模型有更大的表达空间。

但这不等于：

```text
维度越多，检索效果一定越好。
```

真实工程里要看：

- embedding 模型质量。
- 训练数据和业务领域是否匹配。
- chunk 切分是否合理。
- 检索指标是否提升。
- 存储和计算成本是否能接受。
- 索引性能是否稳定。

所以更准确的说法是：

```text
向量维度要够用，但不是越高越好。
```

### 1. 向量维度代表什么？

向量维度可以理解成：

```text
模型用多少个数字来表示一段数据。
```

例如：

```text
384 维：用 384 个数字表示一段文本
768 维：用 768 个数字表示一段文本
1536 维：用 1536 个数字表示一段文本
```

维度越高，理论上能承载的特征空间越大。

就像描述一个人：

```text
只用 3 个字段：姓名、年龄、城市
用 30 个字段：职业、兴趣、学历、技能、语言、偏好……
```

字段更多，表达能力可能更强。

但字段更多也不一定意味着描述更准确。

如果字段质量很差，或者很多字段都是噪声，反而会增加干扰。

向量维度也是类似。

### 2. 高维度的优势

更高维向量可能带来一些优势。

第一，表达能力更强。

它有更多数字位置来承载语义特征。

复杂文本、长句、专业领域概念，可能需要更丰富的表示空间。

第二，区分能力可能更好。

例如：

```text
婚假材料
婚假天数
年假材料
报销材料
```

这些内容彼此相似，但细节不同。

更好的高维 embedding 模型可能更容易区分这些细粒度差异。

第三，对复杂语义关系可能更友好。

例如法律、医疗、代码、科研论文等场景，文本含义更密集。

高质量高维模型可能能保留更多细节。

注意这里反复说的是：

```text
高质量高维模型。
```

不是随便把维度变高就有用。

### 3. 高维度的成本

维度越高，成本也会增加。

第一，存储成本增加。

假设每个维度用 float32，占 4 字节。

```text
768 维  ≈ 768 * 4  = 3072 字节 ≈ 3 KB
1536 维 ≈ 1536 * 4 = 6144 字节 ≈ 6 KB
3072 维 ≈ 3072 * 4 = 12288 字节 ≈ 12 KB
```

如果有 100 万个 chunk：

```text
768 维 约 3 GB
1536 维约 6 GB
3072 维约 12 GB
```

这还只是向量本身，没有算索引、metadata、原文、副本。

第二，计算成本增加。

点乘要逐维计算：

```text
score = sum(query[i] * doc[i])
```

维度越高，每次相似度计算需要的乘法和加法越多。

第三，索引成本增加。

高维向量会让索引结构更大，构建和查询都可能更重。

第四，网络传输和缓存压力增加。

向量越大，写入、读取、备份、迁移都更费资源。

### 4. 高维度可能带来噪声

维度更多不一定全是有效信息。

如果模型训练不好，或者和业务领域不匹配，高维空间里可能混入很多无用特征。

这会导致：

```text
看起来数字更多，
但有效语义没有更清楚。
```

甚至可能出现：

- 相似内容没有更近。
- 不相关内容也被拉近。
- 检索结果更难解释。
- 索引更慢但效果没提升。

这就是为什么不能只看维度。

真正要看：

```text
召回率有没有提升？
答案命中率有没有提升？
误召回有没有减少？
延迟和成本是否可接受？
```

### 5. 维度和模型质量不能混为一谈

一个常见误区是：

```text
1536 维模型一定比 768 维模型好。
```

不一定。

更高维只是模型输出形式的一部分。

效果还取决于：

- 模型架构。
- 训练数据。
- 训练目标。
- 是否针对检索优化。
- 中文能力。
- 领域数据覆盖。
- 是否做过对比学习。
- 是否适合短文本或长文本。

可能出现这种情况：

```text
一个 768 维的优秀中文 embedding 模型，
在中文企业知识库上，
比一个 1536 维但领域不匹配的模型效果更好。
```

所以选 embedding 模型不能只看维度。

要做评测。

### 6. 维度和数据规模的关系

数据规模不同，维度选择的压力也不同。

如果只有几千个 chunk：

```text
维度高一点，成本可能还能接受。
```

如果有几千万个 chunk：

```text
维度翻倍会带来非常明显的存储和计算压力。
```

例如：

```text
1000 个 chunk：3 KB 和 6 KB 差别不大
1000 万个 chunk：30 GB 和 60 GB 差别很大
```

所以规模越大，越要认真评估：

- 是否需要这么高维。
- 是否可以用更轻量模型。
- 是否需要压缩或量化。
- 是否需要分片和冷热数据分层。
- 是否需要 rerank 弥补召回阶段的轻量化。

### 7. 低维度是不是一定差？

也不是。

低维向量的优势是：

- 存储更省。
- 查询更快。
- 索引更轻。
- 部署成本更低。

如果任务比较简单，例如：

```text
FAQ 检索
短句相似度
小规模知识库
分类较清晰的内部文档
```

低维模型可能已经够用。

但如果任务复杂，例如：

```text
多领域混合知识库
法律合同检索
代码语义检索
科研论文问答
长文本细粒度召回
```

可能需要更强的 embedding 模型和更合适的维度。

### 8. 降维和压缩

有时为了降低成本，会对向量做压缩。

常见思路包括：

- 使用更低维的 embedding 模型。
- 对向量做降维。
- 使用 float16 代替 float32。
- 使用量化。
- 使用 PQ 这类压缩索引。

压缩的代价是：

```text
可能损失一部分检索精度。
```

所以它也是一个工程权衡：

```text
成本下降多少？
召回率损失多少？
延迟改善多少？
业务是否接受？
```

不要为了省资源盲目压缩，也不要为了追求高精度无限堆成本。

### 9. 应该怎么选择维度？

学习阶段可以记一个简单流程。

第一步，先选适合业务语言和领域的 embedding 模型。

例如中文知识库，要优先看中文检索效果。

第二步，准备评测集。

评测集至少包含：

```text
用户问题
正确应该召回的文档片段
不应该召回的干扰片段
```

第三步，对比不同模型和维度。

观察：

- top_k 命中率。
- 召回率。
- MRR / NDCG 等排序指标。
- 错误召回样例。
- 查询延迟。
- 存储成本。

第四步，结合 rerank 和 Prompt 效果一起看。

因为 RAG 不是只看向量召回。

有时候：

```text
中等维度 embedding + reranker
```

会比：

```text
超高维 embedding 直接 top_k
```

更稳。

### 10. 面试里怎么回答？

可以这样说：

```text
向量维度不是越多越好。更高维度通常有更强的表达空间，可能保留更多语义细节，但也会增加存储、计算、索引和网络成本，还可能引入噪声。真正要看 embedding 模型在业务评测集上的召回率、排序质量、延迟和成本。工程上通常会在效果和资源之间做权衡，而不是单纯追求高维度。
```

更短一点：

```text
维度要够表达语义，但不是越高越好；最终看评测效果和工程成本。
```

### 11. 本节小结

这一节记住五句话：

```text
1. 向量维度更多，表达空间可能更大，但不保证效果更好。
2. 高维度会增加存储、计算、索引和传输成本。
3. 模型质量、训练数据和业务匹配度比单纯维度更重要。
4. 低维模型在简单任务和小规模知识库里可能已经够用。
5. 维度选择要靠评测集验证，而不是凭感觉。
```

## 08 一本 10w 字的书是如何进行向量化的？

先给结论：

```text
一本 10w 字的书，不是直接整体生成一个向量。
```

更合理的做法是：

```text
先解析成文本，
再按章节、段落和语义切成多个 chunk，
每个 chunk 单独生成向量，
最后把 chunk、向量和 metadata 一起存入向量数据库。
```

也就是说：

```text
一本书 -> 很多个 chunk -> 很多个向量
```

而不是：

```text
一本书 -> 一个向量
```

### 1. 为什么不能整本书生成一个向量？

一本 10w 字的书通常包含大量主题。

例如一本 AI 教材可能包括：

```text
Python 基础
LLM 原理
Prompt
RAG
向量数据库
Agent
项目实战
```

如果整本书只生成一个向量，这个向量会非常“平均”。

它很难准确代表某个具体问题。

用户问：

```text
向量数据库里的 HNSW 是什么？
```

如果只有整本书向量，系统只能知道：

```text
这本书大概和 AI 有关。
```

但它很难定位到：

```text
第 8 章第 3 节讲 HNSW 的那几段。
```

RAG 需要的是精确召回相关片段。

所以长书必须切分。

### 2. 整体流程

一本书向量化可以分成 8 步：

```text
1. 文件解析
2. 文本清洗
3. 结构识别
4. 文档切分
5. chunk 增强
6. embedding 生成
7. 向量入库
8. 检索验证
```

展开就是：

```text
PDF / Word / Markdown / EPUB
  ↓
解析成正文文本
  ↓
清洗页眉、页脚、目录、乱码
  ↓
识别标题、章节、段落、页码
  ↓
按语义切成 chunk
  ↓
给 chunk 补充标题和上下文
  ↓
调用 embedding 模型生成向量
  ↓
存入向量数据库
  ↓
用测试问题验证召回效果
```

### 3. 第一步：文件解析

书可能来自不同格式：

- PDF。
- Word。
- Markdown。
- EPUB。
- HTML。
- 扫描版图片。

不同格式解析难度不同。

Markdown 通常最简单，因为标题和段落结构清楚。

PDF 可能会遇到：

- 页眉页脚。
- 分栏。
- 脚注。
- 表格。
- 图片说明。
- 目录。
- 乱码。
- 换行断句。

扫描版 PDF 还需要 OCR。

所以第一步目标是：

```text
尽量得到干净、连续、有结构的正文文本。
```

如果这一步质量差，后面的 embedding 和检索都会受影响。

### 4. 第二步：文本清洗

解析出来的文本通常不能直接入库。

需要清洗：

- 去掉重复页眉页脚。
- 去掉页码。
- 修复错误换行。
- 清理目录。
- 清理乱码。
- 合并被拆断的句子。
- 保留必要的标题。
- 保留图表说明。
- 标记代码块或表格。

例如 PDF 解析后可能是：

```text
向量数据库
第 128 页
的索引机制通常使用
HNSW
或 IVF。
```

清洗后应该变成：

```text
向量数据库的索引机制通常使用 HNSW 或 IVF。
```

清洗不是小事。

RAG 项目里很多检索问题，其实不是模型问题，而是文档解析和清洗问题。

### 5. 第三步：结构识别

一本书有天然结构：

```text
书名
章
节
小节
段落
页码
图表
代码块
脚注
```

结构识别的目的，是让每个 chunk 都知道自己来自哪里。

例如：

```json
{
  "bookTitle": "AI 架构课",
  "chapter": "08 向量数据库原理解析",
  "section": "03 向量数据库的索引机制",
  "pageStart": 120,
  "pageEnd": 121
}
```

这些信息后面可以用于：

- 引用来源。
- 章节过滤。
- 上下文拼接。
- 错误排查。
- 用户点击回到原文。

不要只存一段孤立文本。

要保留它在书里的位置。

### 6. 第四步：文档切分

切分是 10w 字书籍向量化的核心。

切得太大：

```text
一个 chunk 包含太多主题，向量不聚焦。
```

切得太小：

```text
一个 chunk 信息不完整，模型回答缺上下文。
```

常见切分策略：

```text
按章节切
按标题切
按段落切
按 token 长度切
按语义边界切
加 overlap 重叠
```

学习阶段可以先用一个简单策略：

```text
优先按标题和段落切；
每个 chunk 控制在 500-1000 中文字左右；
相邻 chunk 保留 50-150 字 overlap；
每个 chunk 附带当前章节标题。
```

这不是绝对标准，只是一个起点。

实际要根据书的类型调整。

### 7. 10w 字大概会切成多少 chunk？

粗略估算：

```text
书总字数：100000 字
每个 chunk：800 字
overlap：100 字
有效步长：700 字
```

chunk 数量大约：

```text
100000 / 700 ≈ 143 个 chunk
```

如果每个 chunk 500 字、overlap 100 字：

```text
100000 / 400 ≈ 250 个 chunk
```

所以一本 10w 字的书，通常可能产生：

```text
100-300 个 chunk
```

具体数量取决于：

- 章节结构。
- 段落长短。
- chunk 大小。
- overlap 长度。
- 是否拆表格和代码。
- 是否保留摘要和标题。

### 8. 第五步：chunk 增强

chunk 不能只保留正文。

很多时候要给 chunk 补充上下文。

例如原文段落是：

```text
它的主要优点是查询速度快，召回效果好。
```

如果单独拿出来，读者不知道“它”是什么。

更好的 chunk 内容可能是：

```text
章节：向量数据库的索引机制
小节：HNSW 的直觉
正文：HNSW 的主要优点是查询速度快，召回效果好。
```

这种做法叫上下文增强。

目的就是让 embedding 模型看到更多语义线索。

常见增强方式：

- 在 chunk 前加章节标题。
- 加小节标题。
- 加文档标题。
- 保留上一小段过渡文本。
- 给表格添加表名和字段说明。
- 给代码块添加文件名或函数名。

### 9. 第六步：生成 embedding

每个 chunk 都要单独调用 embedding 模型。

伪代码：

```text
chunks = split_book(book_text)

for chunk in chunks:
    vector = embedding_model.embed(chunk.content_for_embedding)
    save({
        chunkId: chunk.id,
        content: chunk.original_content,
        vector: vector,
        metadata: chunk.metadata
    })
```

注意这里有两个 content：

```text
content_for_embedding：用于生成向量，可能带标题和上下文增强。
original_content：用于展示和引用，尽量保持原文。
```

二者可以相同，也可以不同。

工程上常见做法是：

```text
检索时用增强文本 embedding；
展示时返回原始正文和来源。
```

### 10. 第七步：向量入库

每个 chunk 入库时，至少要保存：

```text
chunkId
bookId
bookTitle
chapter
section
pageStart
pageEnd
content
contentForEmbedding
vector
embeddingModel
dimension
metadata
```

示例：

```json
{
  "chunkId": "book_ai_001_ch08_sec03_0007",
  "bookId": "book_ai_001",
  "bookTitle": "AI 架构课",
  "chapter": "08 向量数据库原理解析",
  "section": "03 向量数据库的索引机制",
  "pageStart": 120,
  "pageEnd": 121,
  "content": "HNSW 可以理解成给向量之间建立一张近邻图……",
  "contentForEmbedding": "章节：08 向量数据库原理解析\n小节：03 向量数据库的索引机制\n正文：HNSW 可以理解成给向量之间建立一张近邻图……",
  "vector": [0.031, -0.128, 0.556],
  "embeddingModel": "text-embedding-model",
  "dimension": 3,
  "metadata": {
    "type": "book",
    "language": "zh",
    "chunkIndex": 7
  }
}
```

真实 vector 维度会更高，这里只是示意。

### 11. 第八步：检索验证

入库后不能直接认为完成。

要用问题测试召回效果。

例如：

```text
HNSW 是什么？
向量维度越多越好吗？
一本书为什么不能只生成一个向量？
点乘查询怎么计算？
```

检查：

```text
top_1 是否命中正确片段？
top_5 是否包含正确片段？
召回片段是否过长或过短？
是否缺少章节标题导致语义不清？
是否返回了相邻但不回答问题的片段？
```

如果效果不好，可能要调整：

- chunk 大小。
- overlap。
- 是否加标题。
- embedding 模型。
- top_k。
- reranker。
- metadata 过滤。

### 12. 查询时如何使用这些向量？

用户问：

```text
向量数据库为什么需要索引？
```

系统会：

```text
1. 把问题转成 query_vector
2. 在书籍 chunk 向量库中检索 top_k
3. 返回相关 chunk
4. 组装 Prompt
5. 让 LLM 基于 chunk 回答
6. 附上书名、章节、页码或段落引用
```

最终 Prompt 可能包含：

```text
用户问题：
向量数据库为什么需要索引？

参考资料：
[来源：AI 架构课 / 第 08 章 / 03 向量数据库的索引机制 / 第 120 页]
如果每次查询都和所有向量做一遍点乘，成本会非常高。所以向量数据库需要索引……
```

LLM 再基于这些资料生成答案。

这才是 RAG 的完整意义：

```text
先定位书里的相关片段，再基于片段回答。
```

### 13. 书籍向量化的常见错误

常见错误包括：

- 整本书只生成一个向量。
- 按固定字数硬切，切断标题、表格或代码。
- chunk 太大，召回内容不聚焦。
- chunk 太小，缺少上下文。
- 不保留章节和页码，无法引用。
- 不清理页眉页脚，噪声进入向量。
- 文档和 query 使用不同 embedding 模型。
- 没有测试问题集，入库后不知道效果。
- 只看 top_k 分数，不人工检查召回内容。

书籍向量化的难点不在于“调用 embedding API”。

真正难的是：

```text
把书处理成适合检索的知识单元。
```

### 14. 面试里怎么回答？

可以这样说：

```text
一本 10w 字的书不会直接整体生成一个向量，而是先解析和清洗文本，再按章节、标题、段落和 token 长度切成多个语义完整的 chunk。每个 chunk 会带上书名、章节、页码等 metadata，单独调用 embedding 模型生成向量，然后把 content、vector、metadata、embeddingModel 和 dimension 存入向量数据库。查询时把用户问题也转成向量，检索相关 chunk，再让 LLM 基于这些片段回答并返回引用来源。
```

更短一点：

```text
一本书向量化，本质是把整本书拆成可检索的 chunk，再给每个 chunk 生成向量并带来源入库。
```

### 15. 本节小结

这一节记住五句话：

```text
1. 10w 字的书不能只生成一个向量。
2. 正确做法是解析、清洗、结构识别、切分 chunk、生成 embedding、入库。
3. chunk 要尽量语义完整，并保留章节、页码和来源。
4. 一本 10w 字的书可能产生 100-300 个 chunk，具体取决于切分策略。
5. 入库后要用测试问题验证召回效果，再调整 chunk、overlap、模型和 top_k。
```

## 09 返回的内容太长了怎么办？

RAG 检索时，经常会遇到一个问题：

```text
向量数据库返回了很多相关 chunk，
但这些 chunk 加起来太长，不能全部塞进 Prompt。
```

例如：

```text
top_k = 10
每个 chunk 1000 字
```

那就是：

```text
10000 字参考资料
```

再加上 system prompt、用户问题、历史消息、输出预算，很容易超过上下文限制，或者虽然没超过，但噪声太多，模型反而答不好。

所以这节要讲的是：

```text
检索结果太长时，如何控制进入 LLM 的上下文。
```

核心结论：

```text
不要把所有检索结果无脑塞给模型。
要筛选、重排、压缩、合并和分阶段处理。
```

### 1. 为什么返回内容会太长？

常见原因有几个。

第一，top_k 设置太大。

例如：

```text
top_k = 30
```

可能会召回很多“有点相关，但不一定能回答问题”的片段。

第二，chunk 切得太大。

例如每个 chunk 2000-3000 字。

一个 chunk 里可能包含多个主题。

第三，overlap 太多。

相邻 chunk 大量重复，导致返回结果里出现很多相似内容。

第四，问题太宽泛。

例如：

```text
请总结这本书的 RAG 相关内容。
```

这类问题本来就会命中很多章节。

第五，没有 rerank。

向量召回只做粗排，可能把很多看起来相似但不够精准的内容放进 top_k。

### 2. 第一招：控制 top_k

最直接的方法是控制召回数量。

例如：

```text
top_k = 3
top_k = 5
top_k = 8
```

不要一上来就设很大。

可以这样理解：

```text
top_k 越小：上下文更短，但可能漏召回。
top_k 越大：召回更全，但噪声和成本更高。
```

真实项目里，top_k 要通过评测调。

例如准备 50 个测试问题，观察：

```text
top_3 是否命中正确片段？
top_5 是否命中正确片段？
top_10 是否带来太多噪声？
```

如果 top_5 已经能稳定命中，就没必要默认 top_20。

### 3. 第二招：用 rerank 精排

向量检索通常是召回阶段。

它的目标是：

```text
先找出可能相关的一批候选。
```

但这批候选里，不一定每个都适合放进 Prompt。

所以常见做法是：

```text
先召回较多候选；
再用 reranker 重新排序；
最后只取前几个进入 Prompt。
```

例如：

```text
向量召回 top_20
reranker 重排 top_20
最终放入 Prompt top_5
```

reranker 会更仔细地判断：

```text
这个 chunk 是否真的能回答用户问题？
```

这比单纯看向量相似度更稳。

### 4. 第三招：按 token 预算裁剪

进入 LLM 的上下文应该有预算。

例如总上下文预算是：

```text
16000 token
```

可能要分配成：

```text
system prompt：1000 token
历史消息：2000 token
用户问题：500 token
检索资料：8000 token
输出预留：4500 token
```

也就是说，检索资料不能无限放。

可以设计一个 Context Builder：

```text
按照 rerank 分数从高到低加入 chunk；
每加入一个 chunk 就计算 token；
超过预算就停止；
保证给输出保留足够 token。
```

伪代码：

```text
budget = 8000
context = []
used = 0

for chunk in reranked_chunks:
    tokens = count_tokens(chunk.content)
    if used + tokens > budget:
        continue
    context.append(chunk)
    used += tokens
```

这叫上下文预算管理。

### 5. 第四招：压缩检索结果

如果召回内容都重要，但太长，可以先压缩。

压缩方式有两种。

第一种是抽取式压缩。

```text
只保留和问题最相关的句子、段落、表格行。
```

例如 chunk 很长：

```text
本章介绍请假制度，包括年假、病假、婚假、产假、调休假……
婚假为 10 天，申请时需要提交结婚证复印件……
员工请年假需提前 3 个工作日申请……
```

用户问婚假材料。

压缩后只保留：

```text
婚假为 10 天，申请时需要提交结婚证复印件。
```

第二种是摘要式压缩。

```text
让模型把 chunk 压缩成和问题相关的短摘要。
```

例如：

```text
请基于用户问题，只提取这段资料中可用于回答问题的事实。
```

摘要式压缩要小心。

因为摘要可能丢失细节或引入改写误差。

所以重要场景最好保留原文引用。

### 6. 第五招：合并相邻 chunk

有时返回内容太长，不是因为信息多，而是因为重复多。

例如检索结果命中：

```text
chapter_08_chunk_003
chapter_08_chunk_004
chapter_08_chunk_005
```

它们本来就是连续片段。

如果每个 chunk 都带 overlap，就会重复很多内容。

这时可以做：

```text
相邻 chunk 合并
去掉重复 overlap
保留连续原文
```

这样既能保留上下文，又能减少重复。

尤其是书籍、合同、论文这种长文档，合并相邻 chunk 很常见。

### 7. 第六招：分阶段回答

如果用户问题本身很大，例如：

```text
请总结这本书里所有关于向量数据库的内容。
```

这种问题可能需要很多章节资料。

不要强行一次性塞完。

可以改成分阶段：

```text
1. 先检索相关章节
2. 每个章节生成局部摘要
3. 合并局部摘要
4. 再生成最终回答
5. 保留每个结论的来源
```

这就是 map-reduce 思路：

```text
多段资料 -> 局部处理 -> 汇总处理
```

适合：

- 长书总结。
- 多文档综述。
- 法律合同分析。
- 大量工单归纳。
- 课程知识点汇总。

### 8. 第七招：让用户选择范围

有些问题不是技术上必须一次回答。

而是用户问题太宽。

例如：

```text
讲讲这本书。
```

系统可以先反问或提供范围选项：

```text
你想看整体摘要，还是某一章的重点？
```

或者先返回目录级结果：

```text
我找到了 5 个相关章节：
1. RAG 架构
2. 向量数据库
3. LangChain
4. 项目实战
5. 检索优化
你想先看哪一部分？
```

这叫交互式缩小范围。

它比一次性生成一大坨内容更适合产品体验。

### 9. 第八招：只返回答案需要的证据

RAG 不是把资料原样搬给用户。

更好的输出是：

```text
答案
关键依据
引用来源
```

例如用户问：

```text
婚假需要什么材料？
```

不需要返回整章请假制度。

只需要：

```text
根据员工手册，请婚假需要提交结婚证复印件。

依据：
- 员工手册 / 请假制度 / 婚假：婚假为 10 天，申请时需要提交结婚证复印件。
```

也就是说，返回给用户的内容也要控制。

不是检索到多少，就展示多少。

### 10. 一套推荐处理链路

可以把检索结果太长的问题，设计成一条链路：

```text
用户问题
  ↓
向量召回 top_20
  ↓
metadata / 权限过滤
  ↓
rerank 重排
  ↓
相邻 chunk 合并和去重
  ↓
按 token 预算选择 top_n
  ↓
必要时做 query-focused 压缩
  ↓
组装 Prompt
  ↓
LLM 基于资料回答
  ↓
返回答案和引用来源
```

这条链路的目标是：

```text
让模型看到足够回答问题的资料，
但不要看到太多无关资料。
```

### 11. 常见错误

常见错误包括：

- top_k 设置过大。
- 不做 rerank。
- 不计算 token 预算。
- 检索结果全塞进 Prompt。
- overlap 重复内容不去重。
- 压缩时丢失关键数字、日期、条款。
- 摘要替代原文，导致无法引用。
- 问题很宽泛却强行一次回答。
- 没有给模型保留足够输出 token。

这里特别注意一句：

```text
上下文越多，不等于答案越好。
```

太多无关资料会干扰模型。

### 12. 面试里怎么回答？

可以这样说：

```text
如果 RAG 检索返回内容太长，不能直接全部塞进 Prompt。通常会先控制 top_k，再通过 metadata 和权限过滤、rerank 精排、相邻 chunk 合并去重、token 预算裁剪和 query-focused 压缩来控制上下文长度。对于特别大的问题，可以分阶段处理，先对多个 chunk 做局部摘要，再汇总生成最终答案，同时保留原文引用来源。
```

更短一点：

```text
返回内容太长时，要做上下文预算管理：少召回、精排序、去重复、压缩、分阶段，而不是全塞给模型。
```

### 13. 本节小结

这一节记住五句话：

```text
1. 检索结果太长时，不要无脑塞进 Prompt。
2. top_k、chunk 大小、overlap 和问题范围都会影响返回长度。
3. 常用方法是 rerank、token 预算裁剪、去重合并和 query-focused 压缩。
4. 大范围问题适合分阶段处理，先局部摘要再整体汇总。
5. 最终给模型的是足够回答问题的证据，不是越多越好。
```

## 11 大量短句如何向量化？

大量短句向量化，是 RAG 和语义搜索里很常见的场景。

例如：

```text
怎么退款？
发票怎么开？
婚假几天？
账号无法登录。
订单多久发货？
HNSW 是什么？
```

这些句子都很短。

短句不是不能向量化。

真正的问题是：

```text
短句语义信息少，容易缺上下文。
```

所以大量短句向量化的核心不是“每句都丢给 embedding 模型”这么简单，而是要判断：

```text
这句话能不能独立表达完整语义？
如果不能，要不要补上下文？
如果短句之间高度相似，要不要去重、聚类或合并？
```

### 1. 短句向量化的基本原则

先记一个总原则：

```text
能独立表达语义的短句，可以单独向量化。
不能独立表达语义的短句，要补上下文后再向量化。
```

例如：

```text
退款流程说明
```

这句话可以独立表达主题。

可以直接向量化。

但下面这种就不太适合直接向量化：

```text
这个怎么办？
怎么处理？
需要什么？
```

这些句子没有上下文。

单独生成向量后，模型也很难知道“这个”指什么。

更好的做法是补充上下文：

```text
场景：订单退款
问题：这个怎么办？
增强后：订单退款失败怎么办？
```

### 2. 哪些短句适合单独向量化？

适合单独向量化的短句通常有明确语义。

例如：

- FAQ 问题。
- 搜索 query。
- 文档标题。
- 工单标题。
- 产品功能名。
- 错误提示。
- 意图标签。
- 标准问法。

例如：

```text
如何申请婚假？
报销发票过期怎么办？
账号密码忘了怎么找回？
向量数据库为什么需要索引？
```

这些短句本身已经表达了明确问题。

可以每条生成一个向量。

结构可以这样：

```json
{
  "id": "faq_001",
  "content": "如何申请婚假？",
  "vector": [0.031, -0.128, 0.556],
  "metadata": {
    "type": "faq_question",
    "category": "请假制度"
  }
}
```

### 3. 哪些短句不适合直接向量化？

不适合直接向量化的短句，通常缺少上下文。

例如：

```text
打不开。
不行。
没有。
需要什么材料？
这个怎么弄？
异常。
失败。
```

这些短句单独看很模糊。

它们可能来自不同场景：

```text
账号打不开
网页打不开
订单打不开
文件打不开
```

如果直接向量化：

```text
打不开。
```

它的向量会很泛。

检索时容易乱召回。

更好的方式是补充上下文：

```text
场景：账号登录
原句：打不开。
增强文本：账号登录页面打不开。
```

或者：

```text
工单标题：页面打不开
工单分类：账号登录
工单描述：用户进入登录页后提示 502
用于 embedding：账号登录问题：页面打不开，进入登录页后提示 502。
```

### 4. FAQ 短句如何向量化？

FAQ 是大量短句里最典型的场景。

假设有一条 FAQ：

```text
Q：婚假需要提交什么材料？
A：需要提交结婚证复印件。
分类：请假制度
```

可以有三种向量化方式。

第一，只向量化问题。

```text
婚假需要提交什么材料？
```

适合：

```text
用户问题和 FAQ 问法很接近。
```

第二，向量化问题 + 答案。

```text
问题：婚假需要提交什么材料？
答案：需要提交结婚证复印件。
```

适合：

```text
希望向量里包含答案语义。
```

第三，向量化分类 + 问题 + 答案。

```text
分类：请假制度
问题：婚假需要提交什么材料？
答案：需要提交结婚证复印件。
```

适合：

```text
FAQ 很短，需要补业务场景。
```

学习阶段可以优先用第三种。

因为它上下文更完整。

### 5. 工单短句如何向量化？

工单标题通常很短：

```text
登录失败
无法付款
发票开不了
页面报错
```

如果只有标题，语义不够。

更好的向量化文本应该组合多个字段：

```text
标题 + 分类 + 描述 + 关键标签
```

例如：

```json
{
  "ticketId": "ticket_001",
  "title": "登录失败",
  "category": "账号问题",
  "description": "用户使用手机号验证码登录时提示验证码错误。",
  "tags": ["登录", "验证码", "手机号"]
}
```

用于 embedding 的文本可以是：

```text
工单分类：账号问题
标题：登录失败
描述：用户使用手机号验证码登录时提示验证码错误
标签：登录、验证码、手机号
```

这样生成的向量比单独的“登录失败”更稳。

### 6. 标题、标签、关键词如何处理？

标题、标签、关键词很多时候非常短。

例如：

```text
RAG
HNSW
退款
发票
婚假
```

这类内容是否适合向量化，要看用途。

如果目标是精确匹配：

```text
查标签 = RAG
查分类 = 退款
查产品型号 = A123
```

更适合用关键词或数据库字段查询。

如果目标是语义扩展：

```text
退款 ≈ 退钱
发票 ≈ 开票
婚假 ≈ 结婚请假
```

可以向量化。

但最好补上下文：

```text
知识点标签：RAG，含义是检索增强生成。
业务标签：退款，表示用户申请退回订单款项。
制度标签：婚假，表示员工结婚相关假期。
```

短标签直接向量化容易太泛。

补定义后会更稳。

### 7. 大量短句要不要合并？

不建议把大量无关短句随便拼成一个 chunk。

例如：

```text
怎么退款？
怎么请婚假？
HNSW 是什么？
发票怎么开？
账号无法登录。
```

这些问题主题完全不同。

如果合并成一个 chunk，向量会变得很混杂。

检索时可能哪个方向都沾一点，但哪个都不精准。

可以合并的情况是：

```text
同一主题、同一意图、同一问答组。
```

例如同义问法：

```text
怎么退款？
如何申请退款？
退钱入口在哪里？
订单取消后钱怎么退？
```

这些可以聚成一个意图组。

然后为这个组生成一条代表性记录：

```text
意图：申请退款
常见问法：怎么退款？如何申请退款？退钱入口在哪里？订单取消后钱怎么退？
答案：用户可以在订单详情页发起退款申请。
```

这种合并是有语义目的的。

不是简单拼接。

### 8. 去重和聚类很重要

大量短句里通常会有很多重复和近似重复。

例如：

```text
怎么退款？
如何退款？
怎样退钱？
退款怎么操作？
```

如果全部单独入库，会有几个问题：

- 向量库记录变多。
- 检索结果重复。
- top_k 被相似问法挤满。
- 后续 Prompt 里信息重复。

所以可以先做：

```text
文本标准化
去重
近似聚类
意图归并
```

聚类后，每组保留：

```text
标准问法
同义问法列表
标准答案
metadata
```

这样检索更干净。

### 9. 批量向量化怎么做？

大量短句通常不是一条一条手动处理。

工程流程可以是：

```text
1. 收集短句数据
2. 清洗和标准化
3. 判断是否需要补上下文
4. 去重和聚类
5. 构造 content_for_embedding
6. 批量调用 embedding
7. 写入向量数据库
8. 用测试 query 验证召回
```

伪代码：

```text
records = load_short_sentences()

for record in records:
    record.normalized = normalize(record.text)
    record.embeddingText = build_embedding_text(record)

records = deduplicate(records)

batches = split_batches(records, batch_size=100)

for batch in batches:
    vectors = embedding_model.embed(batch.embeddingText)
    vector_db.upsert(batch.ids, vectors, batch.metadata)
```

批量处理时要注意：

- 记录 id 要稳定。
- 失败后可以重试。
- 不要重复写入。
- 保存 embedding 模型版本。
- 保存原始文本和增强文本。

### 10. 短句记录应该存哪些字段？

一条短句向量记录可以这样设计：

```json
{
  "id": "faq_refund_001",
  "rawText": "怎么退款？",
  "embeddingText": "业务场景：订单售后。用户问题：怎么退款？标准意图：申请退款。",
  "vector": [0.031, -0.128, 0.556],
  "metadata": {
    "type": "faq",
    "intent": "refund_request",
    "category": "订单售后",
    "answerId": "answer_refund_001",
    "source": "客服 FAQ",
    "language": "zh"
  }
}
```

其中：

```text
rawText：原始短句，方便展示和排查。
embeddingText：补上下文后的文本，用来生成向量。
metadata：用于过滤、分类、权限和回查答案。
```

不要只存短句本身。

### 11. 检索时如何使用短句向量？

用户问：

```text
我不想买了，钱怎么退？
```

系统流程：

```text
1. 用户问题向量化
2. 在短句/FAQ 向量库中检索
3. metadata 过滤业务范围
4. rerank 精排
5. 找到最接近的标准问题或意图
6. 回查标准答案或关联文档
7. 生成最终回答
```

注意：

```text
短句向量检索经常不是直接返回短句作为答案。
```

它更常用于：

- 找标准问题。
- 找用户意图。
- 找相似工单。
- 找关联答案。
- 找下一步业务流程。

例如检索到：

```text
标准意图：申请退款
answerId：answer_refund_001
```

然后系统再根据 answerId 找完整答案。

### 12. 短句场景常见错误

常见错误包括：

- 所有短句无脑单独向量化。
- 很短、很模糊的句子不补上下文。
- 把不同主题短句拼成一个 chunk。
- 重复问法太多，top_k 被重复内容占满。
- 只做向量检索，不做关键词和 metadata 过滤。
- 对订单号、型号、错误码这类精确字段也强行向量化。
- 不保存原始短句和增强文本，后续无法排查。
- 不区分“检索标准问题”和“检索知识文档”。

短句向量化最容易犯的错就是：

```text
把短句当成长文 chunk 的缩小版。
```

其实短句更需要上下文增强、意图归并和去重。

### 13. 面试里怎么回答？

可以这样说：

```text
大量短句可以向量化，但不能无脑每句直接入库。首先要判断短句是否能独立表达完整语义；像 FAQ 问题、工单标题、标准 query 可以单独向量化，但过短或有指代的句子要补充业务场景、分类、答案或上下文后再生成 embedding。工程上还要做清洗、去重、聚类、构造 embeddingText、批量 embedding、保存 rawText 和 metadata。检索时通常结合向量召回、关键词、metadata 过滤和 rerank，找到标准问题、意图或关联答案。
```

更短一点：

```text
大量短句向量化的关键是补上下文、去重聚类、批量入库；不是把每个短句裸奔式地直接丢给 embedding。
```

### 14. 本节小结

这一节记住五句话：

```text
1. 短句可以向量化，但短句语义薄，常常需要补上下文。
2. 独立完整的 FAQ、query、标题可以单独向量化。
3. 模糊短句要结合分类、场景、描述、答案或父级文档增强。
4. 大量短句要先清洗、去重、聚类，再批量 embedding 入库。
5. 短句检索常用于找意图、标准问题和关联答案，不一定直接作为最终回答。
```
